# Matchmaking V2 — implementation specification

**A6.2. Engineering contract. Nothing here is implemented; V1 stays frozen at `cc6e337`.**

Companion to [matchmaking-v2-spec.md](matchmaking-v2-spec.md) (`c95b8ea`), which owns
the *why*. This document owns the *what*, to the level where two engineers would
build the same thing without making a product decision on the way.

Anything marked **HEURISTIC** is a number chosen by design rather than derived
from data. Every one of them must be labelled as such in code and revisited
against engagement data. Anything marked **DERIVED** is computed from the
repository and re-derivable.

## 2. Result contract

`shared/matching/v2/types.js`. Plain data, no classes, no `null` carrying meaning.

```js
export const GRADE = Object.freeze({
  MEASURED: 'MEASURED',   // every input this component needs was present
  PARTIAL:  'PARTIAL',    // scored from a weaker proxy or known-incomplete data
});                       // ASSUMED is abolished. UNSCOREABLE is not a grade —
                          // it is a different shape (below).

/** A component or layer that produced a number. */
// { ok: true, value: 0..1, grade, coverage: 0..1, basis: {...} }

/** One that did not. Never a number, never null-with-meaning, never NaN. */
// { ok: false, reason: REASON.*, missing: [...], available: [...], coverage }
```

`ok` is the discriminant. Every consumer branches on it; nothing reads `.value`
without checking. A helper `isScoreable(r)` exists so the check is one token.

```js
export const REASON = Object.freeze({
  NO_ROSTER_ON_FILE:        'NO_ROSTER_ON_FILE',
  NO_ELIGIBILITY_RULE:      'NO_ELIGIBILITY_RULE',
  NO_CLASS_LABELS:          'NO_CLASS_LABELS',
  NO_PROGRAMME_LEVEL:       'NO_PROGRAMME_LEVEL',
  NO_ATHLETE_LEVEL:         'NO_ATHLETE_LEVEL',
  NO_COST_BASIS:            'NO_COST_BASIS',
  NO_FAMILY_CONTRIBUTION:   'NO_FAMILY_CONTRIBUTION',
  NO_AID_RULE:              'NO_AID_RULE',
  NOT_APPLICABLE:           'NOT_APPLICABLE',   // e.g. same-country for a domestic athlete
  BELOW_COVERAGE_FLOOR:     'BELOW_COVERAGE_FLOOR',
});
```

`NOT_APPLICABLE` is deliberately distinct from every "we don't know" reason. A
component that does not apply is removed from the denominator **without**
reducing coverage; a component we cannot measure reduces coverage. Conflating
them would penalise a domestic athlete for not being international.

### Programme result

```js
{
  collegeId, name, division, sport,
  eligibility:  { ok: true } | { ok: false, reason, detail },
  recruitability: LayerResult,
  financial:      LayerResult,
  opportunity:    LayerResult,
  pursuitPriority: { ok: true, value: 0..100, gates: {...} } | { ok: false, reason },
  rankingState: RANKING_STATE,
  explain: { ... }          // basis objects only; no prose in the engine
}
```

```js
export const RANKING_STATE = Object.freeze({
  RANKED:      'RANKED',       // every gating layer scoreable; has a pursuit priority
  LIMITED_DATA:'LIMITED_DATA', // eligible, partially evaluated, NO pursuit priority
  INELIGIBLE:  'INELIGIBLE',   // failed a rule — division, conference, academic floor
  SUPPRESSED:  'SUPPRESSED',   // an operator decision in athlete_programmes
});
```

**`INELIGIBLE` and `SUPPRESSED` are separate states**, against the brief's
"INELIGIBLE / SUPPRESSED". They have different provenance (rule vs person),
different reversibility, and different UI: a suppressed programme is one the
operator removed and can restore, and folding it into a rule outcome loses that.

## 3. Coverage mathematics

`shared/matching/v2/coverage.js`. One implementation, used by all three scored layers.

```js
combine(components, { floor })
  applicable  = components where result.reason !== NOT_APPLICABLE
  scoreable   = applicable where ok === true
  coverage    = Σ weight(scoreable) / Σ weight(applicable)
  if (coverage < floor)  → { ok: false, reason: BELOW_COVERAGE_FLOOR, coverage, ... }
  value       = Σ (weight · value)(scoreable) / Σ weight(scoreable)     ← renormalised
  grade       = every scoreable MEASURED ? MEASURED : PARTIAL
```

Two rules that carry the whole design:

1. **`value` and `coverage` are never combined.** No uncertainty penalty, no
   shrinkage toward a prior. A value of 0 at coverage 1.0 is a finding; absence
   of a value is not a worse finding, it is a different kind of statement.
2. **A required component missing makes the layer unscoreable regardless of coverage.**

### Per-layer component tables

**Coach Recruitability** — floor **0.60** *(HEURISTIC)*

| Component | Required | Weight | Unscoreable when |
|---|---|---|---|
| Athletic plausibility | **YES** | ceiling, not a weight | no athlete level or no `soccer_score` |
| Positional opportunity | no | 0.70 | no roster, no eligibility rule, no class labels |
| International propensity | no | 0.30 | `NOT_APPLICABLE` for a domestic athlete |

For a domestic athlete, international propensity is `NOT_APPLICABLE`, so
positional opportunity carries the whole core at full coverage — correct, not a
penalty.

**Financial Viability** — floor **0.50** *(HEURISTIC)*

| Component | Required | Weight | Unscoreable when |
|---|---|---|---|
| Cost basis | **YES** | 1.00 | no net price and no COA |
| Family contribution | **YES** | — (an input, not a term) | `budget_range` absent or `Undeclared` |
| Athletic aid expectation | no | — (an input) | no rule for the association |

Financial viability is a single computed quantity, not a weighted sum; its
"components" are inputs and the floor expresses how many must be present. If
either required input is missing the layer is unscoreable — **there is no
affordable-looking default.**

**Athlete Opportunity** — floor **0.35** *(HEURISTIC, deliberately low)*

| Component | Required | Weight (before priorities) | Unscoreable when |
|---|---|---|---|
| Playing opportunity | no | 0.30 | no roster / no minutes history |
| Academic fit | no | 0.20 | no athlete GPA or test score |
| Major availability | no | 0.15 | `intended_major` absent (**currently always**) |
| Location preference | no | 0.20 | no athlete state and no coordinates |
| Programme trajectory & standing | no | 0.15 | no win rates |

The floor is low because most athlete preferences are uncollected; a
programme should not be pushed into `LIMITED_DATA` because the athlete did not
state a major.

## 4. Ability scale — 1–10 → percentile

`shared/matching/v2/calibration/abilityScale.js` + a pinned JSON table.

**The operator-facing 1–10 input is retained.** What is replaced is
`level = ability × 10`, which maps ratings 1–2 below 0.7% of programmes and
compresses 8, 9 and 10 into the top 6%.

### Percentile targets *(HEURISTIC allocation, DERIVED scores)*

The allocation satisfies two stated requirements, and is checkable against them:
each rating maps to an interpretable division mix, and **ratings 8, 9 and 10
separate the Division I tail**. The percentile targets are a design choice; the
`soccer_score` values are derived from the live distribution.

Compare ratings 8/9/10: `73.4 → 83.5 → 98.8` (men's), three distinct D1 tiers,
against `80 → 90 → 100` under the linear map where all three sat above the 94th
percentile and meant nothing.

**Per sport, not per division.** A single pooled scale is what makes δ comparable
across divisions; a division-relative scale would make a D3 delta and a D1 delta
different quantities and break the ceiling. The two sports differ materially —
women's D1 sits at p70 median against men's p81, because there are 349 women's
D1 programmes and 213 men's — so the table is per sport and must stay so.

### Interpolation and invariants

```js
abilityToPercentile(rating, sport)   // linear interpolation between integer
                                     // targets; clamps to [1,10]
percentileOf(soccerScore, sport)     // empirical CDF from the pinned table
delta = abilityToPercentile(a) − percentileOf(p)      ∈ (−1, 1)
```

Invariants, enforced by test:

1. **Monotone**: `rating → percentile` and `soccer_score → percentile` strictly increasing.
2. **Pinned distribution digest.** The table stores a digest of the
   `soccer_score` distribution it was built from. If the live distribution no
   longer matches, `calibrateAbilityScale.js` must be re-run — **the scale must
   never silently re-derive**, because that would change what a rating *means*
   without anyone deciding to.
3. **Division-mix tolerance.** Each rating's modal division mix is recorded. A
   regeneration that moves any rating's dominant division is a review trigger,
   not an automatic accept.
4. **8/9/10 separation**: the three must map to distinct `soccer_score` values at
   least 5 points apart, or the upper tail has lost its resolution.

## 5. Eligibility

`layers/eligibility.js`. **Wraps V1** rather than reimplementing.

```
eligibility(athlete, college, context) → { ok: true } | { ok: false, reason, detail }
  INELIGIBLE  sport mismatch · college.active === 0 · division not in athlete.divisions
              · conference not in athlete.conferences · academic_rating < academicMinimum
  SUPPRESSED  athlete_programmes.visibility === 'suppressed'
```

**The change from V1**: suppression is applied *here*, before ranking, so a
suppressed programme never consumes one of the hundred. V1 applies it at read
time after the hundred is chosen.

An unrated programme survives an academic floor and is counted, exactly as V1
does — that rule was hard-won and is kept.

Athlete competitive eligibility (years remaining, clearinghouse status) is
**not** assessed: we hold no data. The layer records the gap rather than
guessing.

## 6. Coach Recruitability

### 6.1 Athletic plausibility — structural form vs heuristic parameters

**STRUCTURAL (do not change without re-deriving the model):** monotone,
saturating, bounded (0,1), evaluated in percentile space.

```js
athleticPlausibility({ rating, soccerScore, sport })
  if (rating == null)      → { ok:false, reason: NO_ATHLETE_LEVEL }
  if (soccerScore == null) → { ok:false, reason: NO_PROGRAMME_LEVEL }
  δ = abilityToPercentile(rating, sport) − percentileOf(soccerScore, sport)
  value = 1 / (1 + exp(−(δ − δ₀) / s))
  → { ok:true, value, grade: MEASURED, coverage: 1, basis: { δ, δ₀, s } }
```

**HEURISTIC:** `δ₀ = 0`, `s = 0.12`. Behaviour at those values:

| Athlete | Programme | δ | `A_plaus` |
|---|---|---|---|
| rating 8 (p89) | p96 upper D1 | −0.07 | 0.36 — a genuine reach |
| rating 8 (p89) | p78 low D1 / strong D2 | +0.11 | 0.71 |
| rating 8 (p89) | p50 | +0.39 | 0.96 — saturated |
| rating 3 (p18) | p89 D1 | −0.71 | **0.003** |

A **serious athletic reach** is definable rather than asserted: `A_plaus < 0.15`,
which at `s = 0.12` is roughly 20 percentile points below programme level.

Note the deliberate asymmetry loss: V1 decays above the peak. V2 does not,
because a coach at a weaker programme is not less interested in a stronger
player. The over-qualification concern moves to §8.

### 6.2 Positional opportunity — composite without triple counting

The measured correlations force the shape: openings × group size 0.489,
returning × group size 0.629, arrivals × group size 0.730. **Every count is
normalised by the same denominator, once.**

```js
positionalOpportunity({ rosterIndex, programme, position, entryYear, division, sport })

  avail = positionAvailability(roster, entryYear, position)    // V1 A5.3, reused
  //   { expired, finalSeason, eligibleToRemain, unreadable }

  if (!roster)                 → { ok:false, reason: NO_ROSTER_ON_FILE }
  if (no eligibility rule)     → { ok:false, reason: NO_ELIGIBILITY_RULE }
  if (unreadable share > 0.30) → { ok:false, reason: NO_CLASS_LABELS }

  typical = typicalStarters(programme, position, division, sport)   // lifecycle module
          ?? poolTypicalStarters(position, division, sport)         // DERIVED fallback

  vacatedQuality = Σ projectedMinutes(expired players) / STARTER_MINUTES
  openingWeight  = avail.expired · (1 + λ · vacatedQuality / max(1, avail.expired))
  netNeed        = (openingWeight − avail.eligibleToRemain) / typical
  base           = clamp01(0.5 + 0.5 · netNeed)        // netNeed ∈ [−1,1] → [0,1]

  alreadyRecruited = arrivalsAtPosition(currentCycle) / typical
  intakeDiscount   = clamp01(1 − μ · alreadyRecruited)

  fill = fillPropensity(programme, position)  // openings→newcomer-starter rate
       ?? POOL_FILL                            // DERIVED: 0.459 men's newcomer

  value = base · intakeDiscount · (ν + (1−ν) · fill)
```

Each raw count enters **once**, and always divided by `typical`.

| Parameter | Status | Value |
|---|---|---|
| `λ` vacated-quality weight | HEURISTIC, calibratable today | 0.5 |
| `μ` intake discount | HEURISTIC | 0.5 |
| `ν` fill floor | HEURISTIC | 0.5 |
| `POOL_FILL` | **DERIVED** | 0.459 newcomer / 0.484 freshman, over 4,750 openings |
| `typicalStarters` | **DERIVED** | already computed in `positionUtilisation.js` |
| unreadable-share cut-off 0.30 | HEURISTIC | matches V1's `GRAD_YEAR_NULL_TOLERANCE` |

Coverage floor for `fillPropensity`: ≥3 openings *(the repo's existing
`OPENINGS_FOR_PATTERN`)*. Below it, fall back to the pool rate and grade
`PARTIAL` — **the pool rate is measured, not assumed**, which is why this
fallback is legitimate where a neutral prior is not.

### 6.3 Recruiting behaviour — minimum independent set

Only international propensity survives. Transfer propensity is excluded
(`prior_programme` resolves 16% at D1, 3% at D3 — a rate over that denominator
measures scraping coverage); continuity is excluded (it measures retention,
which has no forward meaning under the 2026 rule change); arrivals-international
share is excluded (r = 0.941 with roster share).

```js
internationalPropensity({ athlete, roster })
  if (athlete.origin !== 'International') → { ok:false, reason: NOT_APPLICABLE }
  if (!roster)                            → { ok:false, reason: NO_ROSTER_ON_FILE }
  share       = internationalRows / rosterRows
  community   = 1 − exp(−share / σ)
  compatriots = sameCountryRows
  countryFit  = athlete.country ? clamp01(compatriots / κ_c) : NOT_APPLICABLE
  value = countryFit applicable ? (c₁·community + c₂·countryFit) : community
```

`σ = 0.2`, `κ_c = 3`, `c₁ = 0.65`, `c₂ = 0.35` — **HEURISTIC**, carried over
from V1 where they were reasoned rather than measured. **The V1 floor of 0.15 is
removed**: a programme with no internationals should score near zero on this
component and be lifted by the ceiling structure, not by a hidden floor.

### 6.4 The ceiling

```js
recruitability(athlete, programme, ctx)
  A = athleticPlausibility(...)
  if (!A.ok) → { ok:false, reason: A.reason, coverage: 0 }

  core = coverage.combine([
    { key:'positionalOpportunity', weight:0.70, result: positionalOpportunity(...) },
    { key:'internationalPropensity', weight:0.30, result: internationalPropensity(...) },
  ], { floor: 0.60 })

  if (!core.ok) → { ok:false, reason: core.reason, coverage: core.coverage,
                    available: ['athleticPlausibility'] }

  value = A.value · (φ + (1 − φ) · core.value)
  → { ok:true, value, grade: worst(A.grade, core.grade), coverage: core.coverage,
      basis: { athletic: A, core } }
```

**`φ = 0.35` — HEURISTIC.** Athletic plausibility appears exactly once, as the
ceiling. `A_plaus = 0.003` (rating 3 at D1) caps recruitability at 0.003 no
matter how large the positional need — which is the requirement, expressed
structurally rather than as a rule.

## 7. Financial Viability

Two modes, one code path. `CURRENT_INPUTS` ships; `FUTURE_ENRICHED_INPUTS` is
designed now so the shape does not change when income band arrives.

```js
financialViability({ athlete, college, division, conference, sport, mode })

  // ---- 1. cost basis -------------------------------------------------
  if (mode === FUTURE_ENRICHED && athlete.incomeBand && bracketNetPrice) {
      costAfterInstitutionalAid = bracketNetPrice[athlete.incomeBand]
      basis = 'INCOME_BRACKET_NET_PRICE'          // need AND typical merit already inside
  } else if (college.net_price != null) {
      costAfterInstitutionalAid = net_price + outOfStatePremium(...)
      basis = 'AVERAGE_NET_PRICE'                  // averaged over all incomes
      grade = PARTIAL                              // it is not this family's price
  } else → { ok:false, reason: NO_COST_BASIS }

  // NO FURTHER AID IS SUBTRACTED HERE. Net price is already cost after grant
  // aid; subtracting need- or merit-based aid again subtracts it twice.

  // ---- 2. residency ---------------------------------------------------
  outOfStatePremium = (control === 1 && athleteState !== schoolState
                       && tuitionOut > tuitionIn) ? tuitionOut − tuitionIn : 0
  // Private institutions charge one price: premium is 0, never a discount.

  // ---- 3. athletic aid ------------------------------------------------
  policy = athleticAidPolicy({ division, sport, conference })     // V1, reused
  if (policy.status === UNKNOWN) { aidExpected = 0; aidGrade = PARTIAL;
                                   aidKnown = false }
  else                          { aidExpected = policy.mean · costAfter…;
                                   aidKnown = true }
  // NO ATHLETIC DELTA. V1 scales the award by how far the athlete sits above
  // the programme; that is the athletic axis entering a third layer.
  // The award RANGE (mean → max) is reported, never scored.

  // ---- 4. family contribution -----------------------------------------
  ceiling = budgetCeiling(athlete.budget_range)
  if (ceiling === undefined) → { ok:false, reason: NO_FAMILY_CONTRIBUTION }
  if (ceiling === Infinity)  → { ok:true, value: 1, grade, coverage,
                                 basis:{ noCeiling:true } }

  // ---- 5. gap and viability -------------------------------------------
  gap   = max(0, costAfterInstitutionalAid − aidExpected − ceiling)
  scale = max(SCALE_MIN, ceiling · 0.6)
  value = φ_F + (1 − φ_F) · exp(−gap / scale)
```

| Parameter | Status | Value |
|---|---|---|
| `φ_F` floor | HEURISTIC | 0.05 *(V1 used 0.20; lowered so a genuinely unaffordable school can reach the gate)* |
| `SCALE_MIN` | HEURISTIC | 8,000 |
| aid mean/max tables | ASSUMED, documented as such in V1 | unchanged |

**Merit context, never score.** `COA − net_price[110k+]` at private institutions
(n=771, median $24,132, p25 $18,316, p75 $31,069, **min $0**) is attached to
`basis` as context and **excluded from `value`**. A lower-bracket family already
has that discount inside their bracket price; adding it again is double counting,
and we hold no evidence of *above-average* merit for a particular athlete. This
is how "strong GPA = more money" stays out structurally.

**Missing-data behaviour — the rule that matters:** no combination of missing
inputs may produce a high score. Missing cost basis or missing family
contribution ⇒ **unscoreable**. Unknown aid policy ⇒ `aidExpected = 0`
(conservative: the school looks *more* expensive, not less) with `PARTIAL` grade
and `aidKnown: false` so no surface quotes an award.

## 8. Athlete Opportunity

```js
opportunity({ athlete, college, roster, ctx })
  components = [
    { key:'playingOpportunity', weight:0.30, result: playingOpportunity(...) },
    { key:'academicFit',        weight:0.20, result: academicFit(...) },
    { key:'majorFit',           weight:0.15, result: majorFit(...) },
    { key:'location',           weight:0.20, result: locationPreference(...) },
    { key:'standing',           weight:0.15, result: programmeStanding(...) },
  ]
  weights = applyPriorities(components, athlete.criterion_ranking)
  return coverage.combine(weights, { floor: 0.35 })
```

### 8.1 Playing opportunity — not a rescaled recruitability term

B owns *counts* of returning players. D must use a **minutes** quantity, or the
same fact is counted twice (§3.4 of the design doc).

```js
playingOpportunity({ roster, position, entryYear, division, sport })
  vacatedMinutes   = Σ projectedMinutes(EXPIRED at position)
  retainedMinutes  = Σ projectedMinutes(ELIGIBLE_TO_REMAIN at position)
  ladder           = firstYearMinutesLadder(programme, position)  // freshmanMinutes.js
  minutesShare     = vacatedMinutes / max(vacatedMinutes + retainedMinutes, ε)
  value            = clamp01(ω · minutesShare + (1−ω) · ladderPercentile)
```

`minutesShare` and `ladder` are both minutes-based and neither is a monotone
function of the counts B uses. **HEURISTIC `ω = 0.5`.**

### 8.2 Athletic outcome attractiveness — where the two-sided relationship lives

Permitted here, and **only** here:

```js
athleticOutcome(δ, athlete.developmentPreference)
  // A two-sided preference: some athletes want to be the standout, others want
  // stretch. Until intake collects it, `developmentPreference` is absent and
  // this component is NOT_APPLICABLE — it does not default to a peak.
```

This is the home of V1's over-qualification decay. It is **not scored today**
because the preference that decides its shape is uncollected — and inventing a
default peak would smuggle V1's Gaussian back in through the other layer.

### 8.3 The remaining components

- **`academicFit`** — `academic_rating` quality × admissibility (SAT/ACT/GPA). Reuse V1's logic, **not V1's module**. Unscoreable with no athlete academics; must not fall back to quality alone (V1 already learned this: it cost 3.2 points of median percentile).
- **`majorFit`** — `notable_majors` × `intended_major`. **Currently always `NOT_APPLICABLE`** since intake does not collect the major; approved for future intake.
- **`locationPreference`** — distance from state centroid, in-state lift. **All of geography lives here.** V1's `need-favours-staying-in-state` coupling is **deleted**: the in-state benefit is priced once, in §7.
- **`programmeStanding`** — trajectory (`recent − prior` win rate), postseason round, conference title. **Programme level is absent by design** (r = +0.893 / −0.864 with athletic fit). Win-rate *level* excluded (r = 0.399 with `soccer_score`).

### 8.4 How priorities alter weights

`criterion_ranking` reweights **inside this layer only**. Geometric decay, as V1
established (`RANKING_DECAY = 0.65`), applied to the five components above, then
renormalised over what is scoreable. It does **not** touch the layer weights in
§9: an athlete cannot prefer their way into being recruitable.

## 9. Pursuit Priority

```js
pursuitPriority({ recruitability: R, financial: F, opportunity: O })

  gating = [R, F]
  if (gating.some(l => !l.ok)) → { ok:false, reason: 'GATING_LAYER_UNSCOREABLE',
                                   unscoreable: gating.filter(l=>!l.ok).map(l=>l.key) }

  layers = [ {k:'R', w:W_R, l:R}, {k:'F', w:W_F, l:F}, {k:'O', w:W_O, l:O} ]
  scoreable = layers.filter(x => x.l.ok)
  base = Σ (w · value)(scoreable) / Σ w(scoreable)

  g = (v, κ, γ) => v >= κ ? 1 : (v / κ) ** γ

  value = 100 · base · g(R.value, κ_R, γ_R) · g(F.value, κ_F, γ_F)
```

**Opportunity is never a gate** and may be unscoreable without blocking a rank —
it simply leaves the additive core and the remaining weights renormalise.

| Parameter | Status | Provisional |
|---|---|---|
| `W_R`, `W_F`, `W_O` | **HEURISTIC** | 0.45 / 0.30 / 0.25 |
| `κ_R`, `γ_R` | **HEURISTIC** | 0.30, 1.5 |
| `κ_F`, `γ_F` | **HEURISTIC** | 0.35, 1.5 |

### Expected behaviour, scenarios A–J

| Scenario | R | F | O | base | gated | Reading |
|---|---|---|---|---|---|---|
| A excellent × 3 | .95 | .92 | .93 | 93.6 | **93.6** | top |
| B great recruit, poor finance | .95 | .15 | .95 | 71.0 | **19.9** | demoted, not deleted |
| C poor recruit, great F+O | .18 | .95 | .95 | 60.3 | **28.0** | reach, constrained, visible |
| D strong R+F, poor fit | .85 | .85 | .20 | 68.8 | **68.8** | ungated — fit is not viability |
| E unknown R, rest excellent | — | .92 | .93 | — | **LIMITED_DATA** | no fabricated priority |
| F reach with big need | .30 | .70 | .85 | 55.8 | 55.8 | need cannot outrun the ceiling |
| G target, little need | .62 | .75 | .70 | 67.9 | 67.9 | |
| H cheap strong-academic D3 | .70 | .95 | .72 | 78.0 | **78.0** | |
| I expensive D1 reach | .34 | .22 | .90 | 44.4 | **22.1** | both gates bite |
| J NJCAA, no roster data | — | .90 | .45 | — | **LIMITED_DATA** | |

Resulting order: `A > H > D > G > F > C > I > B`, with E and J outside the

## 10. LIMITED_DATA and the Top 100 pipeline

```
eligiblePool          = colleges − INELIGIBLE − SUPPRESSED
      ↓ evaluate all three layers for every programme
scoreable             = gating layers (R, F) both ok
limitedData           = eligible, not scoreable
      ↓
ranked                = scoreable sorted by pursuitPriority desc,
                        ties → R, then F, then name
actionable            = ranked.slice(0, 100)        ← OUTPUT LIMIT, not a threshold
reserve               = ranked.slice(100, 150)      ← unchanged from V1
limitedData           = sorted separately (below), never interleaved
```

**100 is an output limit applied after ranking, not a cut in the mathematics.**
All scoreable programmes are ranked first.

### Sorting limited-data programmes

The brief's preference — sort on defensible available information and coverage,
never presented as equivalent to Pursuit Priority — is **right, and I have no
cleaner design.** One refinement:

```
sort limitedData by:
  1. coverage of the layers that DID score  (descending)
  2. the value of the highest-coverage scoreable layer
  3. name
```

Sorting on *coverage first* means the ordering answers "how much do we know
about this programme", which is honestly what it is — rather than "how good is
it", which we cannot say. That is a materially different claim from Pursuit
Priority and should be labelled as such wherever it surfaces.

A limited-data programme **retains every layer output it produced**. The UI can
show programme level, cost, distance, academics and whatever opportunity
evidence exists, plus `missing: [...]` naming what is absent. It receives **no
`pursuitPriority`** — the field is `{ ok:false }`, not a number.

**Campaign safety.** `tierForRank` has no band above 100 and `freezeRecommendations`
reads `analysis.recommendations`. Limited-data programmes must be persisted under
a **separate key**, exactly as `reserve` was, so every existing campaign guard
remains blind to them. Do not widen `recommendations`.

## 11. Parallel-run harness

`server/lib/v2/parallelRun.js` + `server/scripts/v2Compare.js`. Read-only,
production-safe, adopting nothing.

```js
compare({ athlete, colleges, rosterIndex, ctx })
  v1 = rankMatches(...)                      // frozen V1, untouched
  v2 = v2Pipeline(...)

```

Diagnostics:

| Metric | Why |
|---|---|
| rank delta per programme; entered / left top 100 | the headline movement |
| division composition, both lists | catches a silent division sweep |
| distribution of `A_plaus`, `R`, `F`, `O` | catches a layer saturating or collapsing |
| coverage distribution per layer | how much of the pool is actually evaluable |

## 12. Regression invariants

Behavioural, not pinned scores, so calibration can move values without rewriting
tests.

**Ceiling and athletic**
1. A clearly under-level athlete (`A_plaus < 0.05`) cannot exceed `R = 0.05` at any positional need, budget or academic profile.
2. Increasing positional need never raises `R` above `A_plaus`.
3. `A_plaus` is monotone non-decreasing in athlete rating, at fixed programme.
4. Rating 8, 9, 10 map to `soccer_score` values ≥5 apart.
5. A strong athlete at a much weaker programme keeps high `R` and **may** score lower on `O` — the two must be able to diverge.

**Evidence**
6. A measured `Need = 0` is scoreable and ranks; it is never converted to missing.
7. A programme with no roster is `LIMITED_DATA`, never `Need = 0.5`.
8. No unscoreable programme appears in the ranked list at any position.
9. `NOT_APPLICABLE` does not reduce coverage; a missing measurement does.
10. `value` and `coverage` are independent: two programmes with equal `value` and different coverage have equal `value`.

**Gating**
11. Poor finance strongly demotes and never deletes: B scores > 0 and outside the top decile.
12. Poor opportunity never gates: D's rank is within a few places of its ungated rank.
13. A gate never fires on an unscoreable layer.

**Eligibility semantics**
14. A D1/D2 senior listed in 2026 is `ELIGIBLE_TO_REMAIN` at entry 2027, never a confirmed opening.
15. A D3/NAIA senior listed in 2026 is `EXPIRED` at entry 2027.
16. A graduate student is `EXPIRED` for 2027 under every association.
17. NJCAA/USCAA yield no eligibility ceiling and land in `LIMITED_DATA`.

**Financial**
18. A private institution in the athlete's home state receives no residency discount.
19. A public institution out of state adds the tuition premium; in state does not.
20. Strong GPA alone never increases `F`.
21. Unknown aid policy never produces a "no scholarships available" claim, and never raises `F`.
22. Missing net price or missing budget ⇒ `F` unscoreable ⇒ `LIMITED_DATA`.
23. No missing-data combination produces `F > 0.5`.

**Pipeline**
24. Suppressed programmes never consume a top-100 slot.
25. `recommendations` never contains a limited-data programme.
26. The actionable list is exactly `min(100, scoreable)`.

## 13. Implementation order — with two challenges

The proposed order is broadly right. Two changes:

**Move the parallel-run harness to position 3.** Building it after every layer
means seven layers land with no way to see what any of them does to a real
ranking. Built early against V1 alone it proves the harness itself; each layer
then lands with immediate visibility.

**Move the limited-data split before pursuit priority.** Gating depends on the
scoreable/unscoreable distinction existing. Building the combination first means
building it against a distinction that is not yet real.

```
 1. types.js + coverage.js                    contract first; nothing compiles without it
 2. abilityScale + calibration script         DERIVED, testable alone, no dependencies
 3. parallelRun skeleton (V1 only)            proves the harness before it is needed
 4. eligibility adapter                       wraps V1; smallest real layer
 5. coverage engine + LIMITED_DATA split      the distinction everything else needs
 6. financial.js                              best coverage, fewest heuristics
 7. opportunity.js                            good coverage; excludes the uncollected
 8. recruitability.js                         most heuristic, most dependencies — last
 9. combine.js                                needs all three layers real
10. explain.js                                basis → prose
11. validation: invariants + parallel run     full pool, both sports
12. owner review → adoption decision
```

Rationale for 6 before 8: financial has 99%+ institutional coverage and its
parameters are mostly rules; recruitability is the dominant layer *and* the most
heuristic, so it should land when the harness can immediately show its effect.

## 15. Unresolved issues

1. **`positionUtilisation` excludes goalkeepers by design** — the median programme uses two and one reaches 600 minutes, so there is no distribution. `typicalStarters` for GK must come from a different derivation (probably a constant of 1) and invariant 4 in §12 needs a GK-specific case.
2. **Cross-sport athletes** — the scale is per sport and an athlete has one sport. Fine today; breaks if an athlete is ever matched across sports.
3. **`soccer_score` is itself a model.** Every δ rests on it, and the pinned digest catches a rebuild but cannot tell us whether the rebuild is better.
4. **Ties in the limited-data ordering** will be common, since coverage is coarse. May need a third key.
5. **Women's rating 6 already touches D1 at 26%.** The two sports' rating semantics genuinely differ; operators rating both need to know that a "6" does not mean the same thing.
6. **No decision yet on whether the operator UI exposes coverage**, or only the engine does.
