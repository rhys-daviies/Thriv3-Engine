## Service architecture

`computeMatchmakingV2(db, player)` — an **adapter around a frozen engine**, with
no scoring of its own. It normalises through the canonical
`buildValidationAthlete` path, builds or reuses `buildPoolContext`, calls
`runPursuit`, and adapts the output. Three places where the product bends to
the engine rather than the reverse:

1. an unresolved contribution is refused, not smoothed over;
2. a refusal carries **no `value` key at all** — not `value: null` — so a
   consumer reaching for a number fails visibly instead of sorting a refusal
   to the bottom as "worst";
3. bands are presentation; the exact rank stays on every programme.

## Cache — and a regression I introduced and fixed

Keyed by sport **and** data identity, in two levels.

The first version keyed on the SUPPORTED corpus digest, which made the warm
path **slower than the work it was caching**: computing that digest reads every
college, roster row and arrival and hashes them (~1,400 ms), so a warm request
spent ~1,000 ms deciding it could skip a ~500 ms build. A cache whose key costs
more than its miss is not a cache.

| level | cost | role |
|---|---|---|
| `corpusChangeToken` | **~0.01 ms** | SQLite `data_version` + `total_changes`; any commit moves it |
| `corpusDigests` | ~1,400 ms | content identity; computed only when level 1 moved |

The token is a *change detector*, not an identity — it moves on writes V2 never
reads. That is the right direction to be wrong in: it costs a rebuild, never a
stale answer. Level 2 then confirms whether the supported universe actually
moved, so a 7B coach write re-verifies and keeps serving the same context and
digest. Test **K4** pins exactly that.

The entry is written only after both reads succeed, so a half-built context
keyed by a digest it does not match cannot be served.

## Contribution precondition

`contributionReadiness` uses the engine's own predicate — `familyContribution`
returns `null` to mean refuse — rather than restating the rule, so the two
cannot drift. `STATED` and `NOT_A_CONSTRAINT` are ready; `NEEDS_CONFIRMATION`
and a wholly unrecorded contribution are not. A malformed pair is its own 422.

Without it the engine would return ~1,400 truthful refusals and a caller would
read an empty list as "no good matches".

## Response contract

Top level: `matcherVersion`, `engineFreeze`, `corpusDigest`, `computedAt`,
`playerId`, `sport`, `season`, `contributionState`, `counts` (poolSize,
supportedUniverse, ranked, limitedData, unsupported), `timings`, `programmes`.

Per programme: `programmeId`, `name`, `division`, `status`, `universe`, the
three layers (state, value, grade, coverage — value and grade only when
scoreable), plus `rank`/`band`/`pursuit`/`pursuitGrade` when RANKED, or
`missingLayers` when not.

**Not exposed:** `basis` blocks, component weights and shares, midranks,
calibration internals, roster rows. Pinned by test R3.

## Bands and the three states

`PRIORITY_OUTREACH` 1–25 · `STRONG_PURSUIT` 26–50 · `VIABLE_CONSIDERATION`
51–100 · `BROADER_UNIVERSE` 101+. Presentation only — no score or ordering is
touched, and the exact rank is on every programme.

`RANKED` · `SUPPORTED_LIMITED_DATA` (carrying the canonical refusal reasons) ·
`UNSUPPORTED_ASSOCIATION` (carrying an explanation phrased as a fact about
Thriv3's rules, never about the institution). Test R5 fails on "bad match",
"poor fit", "low score" or "does not offer" appearing anywhere in a payload.

## Route and errors

`GET /api/players/:id/matchmaking`, mounted after `requireOperator`.

GET because the computation writes nothing and is deterministic — proven
against A8.3 with zero differences; only `computedAt` varies. When A9.2 makes
storing a result an explicit act, that act gets its own POST rather than this
handler acquiring a side effect.

| code | status |
|---|---|
| `PLAYER_NOT_FOUND` | 404 |
| **`CONTRIBUTION_UNRESOLVED`** | **409** |
| `ATHLETE_SPORT_UNKNOWN`, `ATHLETE_PROFILE_INCOMPLETE`, `ATHLETE_PROFILE_INVALID`, `CONTRIBUTION_INVALID`, `EMPTY_PROGRAMME_UNIVERSE` | 422 |
| anything else | 500, logged in full, reported as `Unexpected error.` |

409 rather than 422 because nothing about the request is wrong and nothing
about the athlete is impossible: the record is in a state this operation cannot
run against, and the frontend will branch on the code to render a prompt.

**Access follows the existing model exactly.** `players` is a shared operator
store and `requireOperator` is the whole boundary. `players.created_by_id`
exists but no route or library scopes a read by it — my first test assumed the
column was absent rather than checking its use, and was wrong. The route adds
no scoping of its own, which A3 now pins at the source.

## A defect found by its own test

`football_ability: 0` produced a **500**. `buildValidationAthlete` calls
`abilityToPercentile` while assembling, so calibration threw before the
`missing` list it also produces could be read.

The engine is right: *"A rating outside 1-10 is an intake defect, and silently
pulling it to a boundary would hide it."* The adapter was wrong to let that
surface as a server fault. Required inputs are now checked against the engine's
own `REQUIRED_INPUTS` **before** the builder, and a construction failure
becomes `ATHLETE_PROFILE_INVALID` (422) carrying the engine's own sentence,
which names the field and value and no path or table. Pinned by E3b.
