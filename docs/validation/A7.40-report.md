## 2–3. Historical ingestion path, and there is **no global regression**

The 2026 rosters were acquired 2026-08-26 by `~/Documents/Thriv3/_roster_pipeline` (outside this
repo) into per-division CSVs, then imported by `server/scripts/importRosterSheets.js`.

**The class column is blank in the acquisition CSVs themselves** — 30 schools across the eight files,
matching the database exactly. The importer stored faithfully what the extractor never captured.

**2026 is 98.8% labelled overall — the same as 2022, 2023, 2024 and 2025.** So this is not a
regression in the season's code. It is a *per-site extraction failure with no detection*, which is
why it shipped: every check the run performed was about **rows** — counts, turnover gates, season
identity — and **none was about fields**. 30 programmes are 1.2% of the field and never moved a total.

## 4. Root cause — proven at the DOM

For the largest group the page publishes the roster **twice**:

```
li.sidearm-roster-player        ← list view: name, height, hometown, highschool … and NO class
li.sidearm-list-card-item       ← card view: contains .sidearm-roster-player-academic-year
```

`parse_sidearm_html` selects the **list** items, so `select_one('.sidearm-roster-player-academic-year')`
finds nothing — the field lives in a sibling rendering. Verified on Bates men's: 29 list items, 29
academic-year spans, **0 reachable from the selected items**. `parse_any` prefers whichever parser
yields more players; both yield 29, so the one without the class wins.

Confirmed independently: a plain HTTP fetch of all 30 URLs returns **HTTP 200 for every one**, and
**27 of 30 contain class markers in the raw HTML**. The data was served; the extraction missed it.

## 5. Control comparison — it is not adapter-wide

`sidearm-html` and `table` work 99% and 56% of the time and fail on specific template variants.

## 7. Re-acquisition design

The labels were re-read **from the same URL already stored on each row**, using the pipeline's own
`lib.fetch` + the card markup its extractor overlooks. **Nothing was inferred** — no 2025 carry-forward,
no graduation arithmetic, no teammate distribution. §6's prohibitions are structural here: the applier
has no access to another season.

Matching is exact normalised player name within (programme, sport, season = 2026).

## 8. Prevention — `shared/rosterAcquisitionGuard.js`

`assessFieldCoverage` compares one field's coverage in a new acquisition against **that programme's
own history** and returns `CATASTROPHIC_FIELD_LOSS` / `FIELD_COVERAGE_DROP` / `OK` / `NO_BASELINE`.

**It raises REVIEW and returns no value to write** — asserted by a test that checks the result carries
no `value`, `fill`, `label`, `suggested` or `inferred` key, and that the reason says *confirm at the
source* and *do not fill the field from another season*.

Deliberately narrow: one field, one programme, its own past. `MIN_ROWS = 8` keeps a five-player
partial roster from raising a *field* alarm when its real problem is that it is a five-player roster.
Field-agnostic, so a future position or hometown loss reads the same.
