## 1. The current outreach model, as it actually is

Traced end to end before anything was designed.

```
players
  └── outreach            UNIQUE (athlete_id, coach_id)   96 rows
        │                 match_id, token, sent_at, programme_campaign_id
        └── outreach_send  one MESSAGE, UNIQUE (outreach_id, sequence)   41 rows
              │            state, sent_at, college_name, sport, body_hash
              ├── outreach_send_event    append-only, per message        0 rows
              ├── outbound_send_attempt  append-only, per transport      0 rows
              └── programme_messages     the composed words              0 rows

coaches  6,486          id, school, sport, email      ← CURRENT staffing
tracking_events  127    profile visits, by token      → engagement_rollup (19)

campaigns 0 → programme_campaigns 0 → programme_contact_attempts → outreach
```

The communication layer is complete and in good order. `outreach_send.state`
says what was done; `outreach_send_event` carries what was learned about a
message (`REPLY`, `BOUNCE_HARD`, `TRANSPORT_REFUSED`); `tracking_events` carries
what a coach did with the profile, rolled up by `engagement_rollup`.

**`engagement_rollup` is the precedent that shaped §Q.** It is a rebuildable
derived table rather than a status column, and `programme_campaigns.state`
records why: a derived fact stored in a column "is only true while something
keeps writing [it]: the first missed tick leaves the column asserting a
falsehood every screen repeats."

## 2. The provenance gap, measured

A9.5 reported that outreach keys on `(athlete_id, coach_id)`. Against the live
database the gap is not partial — it is total.

| | |
|---|---|
| outreach relationships | 96 |
| …carrying a `programme_campaign_id` | **0** |
| …carrying a `match_id` | 96 |
| sends | 41 |
| …carrying a `college_name` | **14** |
| distinct `match_id` values | 58 |
| …that name a school existing in **two** sports | **42 (72.4%)** |
| …that resolve to exactly one programme | 16 |

`match_id` holds a bare college **name** — `Clemson`, `Duke`, `Stanford`.
Programme identity everywhere else in this codebase is `(college_name, sport)`.
A name alone is not a programme, and for 72.4% of live outreach it genuinely
cannot be resolved to one.

### The coach cannot supply the missing half

The obvious repair is to read the sport, and the school, off the coach. The
live data refuses it:

| `outreach.match_id` | `coaches.school` |
|---|---|
| Trinity (TX) | **Trinity (CT)** |
| Wheaton (MA) | **Wheaton (IL)** |

Two relationships whose recommendation named one institution and whose coach row
names a different institution of the same name in another state. **At least one
side of each pair is already wrong and no join can say which.** Deriving
programme identity from staffing data is therefore not a theoretical risk on
this database; it is a demonstrated error, and §E's rule is enforced rather than
merely noted.

## 3. The chosen attribution chain

```
matchmaking_run
  └── matchmaking_programme_result
        └── matchmaking_selection        ← immutable, from A9.5
              └── outreach_send          ← A9.6: matchmaking_selection_id
                    └── recruiting_observation
```

**On the message, not on the relationship.** `outreach` is one row per
`(athlete, coach)` pair, created once and reused for ever. The schema already
says what follows: the note on `outreach.programme_campaign_id` calls it
"first created under" and therefore "**NOT** the campaign a message belongs to",
which lives on `outreach_send`, per message. A selection is the same kind of
fact. An athlete written to in March out of one run and in September out of
another has one relationship and two causes.

`REFERENCES matchmaking_selections(id)` with **no `ON DELETE` clause**, so the
delete is refused — matching `coach_id` and `connected_mailbox_id` on the same
table. A provenance chain is only worth having if no link can vanish.

### What is validated before a link is written

1. the selection exists;
2. it belongs to the athlete this message is for;
3. the message already froze its own programme, and it is the **same**
   programme — both halves of the identity;
4. the coach, on the evidence held **at creation time**, is at that programme.

(3) refuses a message whose `college_name` is null rather than filling it in
from the selection. Adopting the selection's spelling would make (4) compare the
selection against itself and pass trivially.

The attachment is **immutable and idempotent**: re-attaching the same selection
is a no-op; re-pointing at a different one is refused by name. `coaches` moving
afterwards changes nothing — tested by moving one and re-reading.

`matchmaking_selections` also gains the append-only trigger its three sibling
ledgers carry. A9.5 called it immutable by construction; now that sends resolve
their rank through it, the database says so.

## 4. Schema tournament

| | historical truth | corrections | multiple events | reply classification | auditability | verdict |
|---|---|---|---|---|---|---|
| **A.** status columns on outreach | last writer wins | overwrites | impossible | one slot | none | rejected |
| **B.** one mutable outcome row | last writer wins | overwrites | impossible | one slot | none | rejected |
| **C.** pure event ledger, no linkage | yes | yes | yes | yes | yes | cannot answer "what came of this run" |
| **D.** stable linkage + append-only observations | yes | yes | yes | yes | yes | **chosen** |

Query complexity is the only cost, and §Q's projection absorbs it in one place.
Storage is negligible. The repo already prefers append-only history in three
tables, each with a trigger enforcing it.

### Why not extend `outreach_send_event`

It is already an append-only observation ledger with `source`, `confidence`,
`observed_at` and a JSON payload, and reusing it was the first thing considered.

1. **Its key is `outreach_send_id NOT NULL`**, and most of what A9.6 records did
   not happen to a message: an athlete commits; a coach says on a call that the
   2027 goalkeeper spot is gone; a consultant records that the family ruled out
   the state. The options would be to block the honest case or invent a send for
   it. This schema already made exactly this judgement about
   `outbound_send_attempt.outreach_send_id`: *"A NOT NULL column would make the
   honest case unrecordable."*
2. **Its scope is written into it** — "THINGS THIS SYSTEM LEARNED ABOUT ONE
   MESSAGE". Recruiting intelligence is a fact about a **programme over time**
   that outlives every message, campaign and athlete it was learned through.
3. **It has no classification provenance**, review state, correction semantics or
   per-kind attribute validation, all of which §I, §J and §P require.
4. **It is load-bearing for execution safety.** `executionRetry.js` reads
   `TRANSPORT_REFUSED` out of it to license a re-send. Its vocabulary is a
   transport vocabulary and is better left one. *(That query filters by `type`,
   so widening the enum would not by itself have broken it — this is a reason to
   keep the table focused, not a defect that was found.)*

So the two are **siblings**. `outreach_send_event` says a reply arrived; the new
table says what the reply meant, and carries who decided that and whether anybody
checked.

## 5. `recruiting_observations`

```sql
athlete_id                NOT NULL  → players (CASCADE)
college_name, sport       NOT NULL  frozen programme identity
college_id

coach_id                  nullable  → coaches        (no ON DELETE)
outreach_send_id          nullable  → outreach_send  (no ON DELETE)
matchmaking_selection_id  nullable  → matchmaking_selections (no ON DELETE)

kind                      NOT NULL  validated in code
attributes                          JSON, validated per kind
note                                human, sensitive, never the machine state

source                    NOT NULL  COACH_REPLY | COACH_CALL | ATHLETE | OPERATOR | PROVIDER
classifier_method         NOT NULL  MANUAL | RULE_BASED | AI_ASSISTED
classifier_version, confidence
review_state              NOT NULL  UNREVIEWED | CONFIRMED | REJECTED
reviewed_by_operator_id, reviewed_at

corrects_observation_id   → self
correction                          SUPERSEDES | RETRACTS
provider_event_id                   UNIQUE where not null

observed_at, recorded_at  NOT NULL
```

**The category is not stored.** It is a total function of `kind`, and a stored
copy is a second account of the same fact — which is, in this schema's own
words, how `outreach_evidence` and `outreach_send` "came to disagree". It is
derived on read and asserted total by the tests.

**The trigger names what may never move** rather than banning `UPDATE` outright.
What a row *claims* is frozen; `review_state`, `reviewed_by_operator_id` and
`reviewed_at` are the only three columns left writable, so a machine
classification can be checked without the claim becoming editable. `IS NOT`
rather than `<>`, so a column going to or from NULL is caught.

## 6. Vocabulary — 21 kinds, three categories

**PROGRAMME_INTEREST** — did this programme want this athlete?
`POSITIVE_REPLY` · `NEUTRAL_REPLY` · `NEGATIVE_REPLY` · `REQUESTED_FILM` ·
`REQUESTED_TRANSCRIPT` · `REQUESTED_CALL` · `INTERESTED` ·
`ROSTER_PLACE_OFFERED` · `FINANCIAL_OFFER` · `DECLINED_ATHLETE`

**RECRUITING_INTELLIGENCE** — what is true of this programme, regardless of this athlete?
`POSITION_FILLED` · `POSITION_NEEDED` · `CLASS_FILLED` ·
`RECRUITING_FUTURE_CLASS` · `ROSTER_COMPLETE` · `NOT_RECRUITING_POSITION` ·
`OTHER_RECRUITING_INFORMATION`

**ATHLETE_OUTCOME** — did this athlete want this programme?
`ATHLETE_INTERESTED` · `ATHLETE_NOT_INTERESTED` · `ATHLETE_WITHDREW` · `COMMITTED`

`DECLINED_ATHLETE`, not `DECLINED`: the bare word does not say who declined, and
the athlete-side refusal is eight lines away in the same file.

### COMMUNICATION is deliberately absent

§G lists `SENT` / `DELIVERED` / `OPENED` / `CLICKED` / `REPLIED`. All five
already exist:

| | where it already lives |
|---|---|
| SENT | `outreach_send.state = ACCEPTED`, with `sent_at` |
| DELIVERED / BOUNCED | `outreach_send_event` `BOUNCE_HARD` / `BOUNCE_SOFT` |
| REPLIED | `outreach_send_event` `REPLY` |
| OPENED / CLICKED | `tracking_events`, rolled up by `engagement_rollup` |

Duplicating them is the error this schema has already paid for once. A9.6 adds
the **interpretation** layer and points at the communication layer.

### Compatibility with the vocabulary already in the product

`campaigns.js` holds seven stop reasons. The four that are *observations* map
without translation:

| existing reason | observation kind |
|---|---|
| `not_recruiting` | `NOT_RECRUITING_POSITION` / `ROSTER_COMPLETE` |
| `not_interested` | `DECLINED_ATHLETE` |
| `athlete_declined` | `ATHLETE_NOT_INTERESTED` |
| `committed_elsewhere` | `COMMITTED` (against where they went) |

`no_contact`, `suppressed` and `operator` are decisions Thriv3 made, not things
it learned, and stay where they are.

`position` is the canonical four from `shared/positions.js`, reused rather than
restated. **Nothing is defaulted.** A recruiting class nobody stated is absent,
never "this year"; an urgency nobody stated is absent, never `LOW`.

## 8. Reply classification (§I)

The schema is usable with **only `MANUAL`**, which is the point. A manual
observation arrives `CONFIRMED` — the person recording it *is* the review. A
rule or model writes `AI_ASSISTED` with a `classifier_version` and `confidence`,
arrives `UNREVIEWED`, and stays there until somebody looks. Every row written
before a model existed keeps saying truthfully that a person decided; added
afterwards, this column would have left every existing row ambiguous.

The original message is **referenced**, not copied: `outreach_send_id` points at
where the body already lives.

## 9. Idempotency (§O) and corrections (§P)

`provider_event_id` carries a `UNIQUE` **partial** index. A provider
redelivering produces no second row and the first is returned unchanged.
Manual observations carry NULL and are outside the index entirely — a coach who
says "still interested" in March and again in June said it twice, and both are
real.

**Corrections point backwards.** §P sketches `retracted_by_event_id`; it cannot
be built here, because writing it onto the *old* row is an `UPDATE` of history —
the one thing the trigger forbids and the design exists to prevent. So a
correction is a **new row naming the one it corrects**:

- `SUPERSEDES` — this replaces that. The old row **was true when made** and still
  belongs in any question about what was believed then.
- `RETRACTS` — that should never have been recorded. It was never true.

A correction must be about the same athlete and the same programme. Nothing
silently flips `NEGATIVE_REPLY` to `POSITIVE_REPLY`: both rows survive, in order.

## 10. Current-state projection (§Q)

Derived on every call, never stored, rebuildable from the rows alone —
`engagement_rollup`'s pattern.

Three axes that never collapse into one number. "The coach is keen" and "the
athlete has gone off it" are both true at once, often.

Excluded from *current* state, each for a different reason:

| | why |
|---|---|
| `REJECTED` | a person looked and said it was wrong |
| retracted | a later row says it should never have been recorded |
| superseded | a later row replaced it — still true of its moment, so still in the history |

`unreviewed: false` additionally excludes machine guesses nobody has checked.

**`null` means nobody has observed anything.** It is not a decline.

## 11. Time (§K)

`observed_at` and `recorded_at` are separate columns. A reply observed on
Tuesday may have been sent on Sunday; a coach saying in June that a position was
filled "in the spring" is a June record of an April fact. Every
recruiting-cycle question keys on `observed_at`; one keyed on the wrong column
is wrong by months. Nothing is reduced to a static programme attribute.

## 12. The two future datasets

**Matchmaking validation (§S).** For a programme result at the time of pursuit —
rank, band, R/F/O, evidence grades, athlete inputs, position, entry year — what
happened? The join is
`matchmaking_runs → matchmaking_programme_results → matchmaking_selections →
outreach_send → recruiting_observations`, every link immutable. Not trained on
in A9.6, and §AA proves it is not read by the engine.

**Coach recruiting intelligence (§T).** `programme × time × position/class →
stated need`, served athlete-independently by
`GET /api/programmes/intelligence`. It could later inform outreach suppression,
timing, coach recommendations and programme recruiting profiles — **none of which
changes V2**, because a programme's stated needs are a fact about the programme
and not a judgement of the athlete who received it. Merging it into the match
score would teach the engine that a filled goalkeeper slot means a weak fit for a
midfielder.

## 13. Outcome funnel (§R) — defined, not scored

`SELECTED → SENT → REPLIED → INTERESTED → CALL → OFFER → COMMITTED`

Each stage is an **independent boolean** over the evidence held, read from
whichever record owns it. Not every recruitment passes through every stage — a
coach who rings the family after one email produces a `CALL` with no `REPLY`, and
a funnel requiring monotonic progress would record that as a failure. Nothing is
weighted and nothing is multiplied.

## 14. Privacy (§V)

The ledger holds programme identity, engine facts and a bounded vocabulary. No
email body, no subject, no coach address, no athlete or guardian contact detail.
The coach is referenced by **id**, so rows stay joinable without carrying an
inbox. `note` is optional, never the machine state, and never present in a
committed fixture.

Asserted at the route, not merely intended: `V1` greps the full response text for
`@`, `email`, `phone`, `address`, `guardian`, `parent`; `V2` asserts no response
key is `body`, `subject`, `generated_body`, `wire_body` or `recipient_email`;
`V3` asserts no error carries a table name, a SQL fragment or a stack.

`npm run scan:committed-pii` — **1,633 files scanned, no committed contact PII**.

## 19. Three things that were wrong before they were right

**The `U10` absence test was too broad.** It banned `position filled` across the
whole panel and failed — correctly, because "Position filled" belongs in the
list of kinds an operator may *record*. The rule is about what the three axes
*assert* when nothing has been observed, and the test now says so. A blanket ban
would have made the vocabulary unrenderable.

**Two teardowns were refused by the new foreign keys.** Deleting a selection a
send points at, and deleting a coach an observation names, both failed with
`FOREIGN KEY constraint failed`. That is the designed behaviour, so the tests now
assert the refusal and clear the dependent row first.

**The first migration copy lost the WAL**, as above.

## 21. Remaining A9.7 work

1. **No production path calls `attachSelectionToSend` yet.** The primitive,
   its validation and its tests exist; wiring it into campaign creation from a
   persisted run is A9.7, and is the step that starts producing `V2_PROVENANCE`
   rows. Stated plainly here for the same reason `appendSendEvent` says
   "NOTHING IN THIS BUILD CALLS THIS WITH A BOUNCE".
2. **Reply ingestion.** `outreach_send_event.REPLY` has no producer. Until a
   mailbox is read, every observation is operator-entered.
3. **Rule-based and AI-assisted classification.** The schema carries the
   provenance; no classifier exists.
4. **A persistent selections browser.** The A9.6 surface shows the selection
   just made; it is not a list.
5. **Operator attribution.** `reviewed_by_operator_id` is accepted and never
   populated, because nothing binds a session to a write — the same gap
   `athlete_programmes.note` records.
6. **Cold start ~1.8 s**, unchanged: the compute path is byte-identical, so it
   was not re-measured.
