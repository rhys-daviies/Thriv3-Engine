## 2. The V2 production path

```
matchmaking_run → matchmaking_programme_result → matchmaking_selection
                → programme_campaigns.matchmaking_selection_id
                → outreach_send.matchmaking_selection_id
                → recruiting_observations
```

Every link immutable; none nullable in a way that loses history.

### Provenance is per programme, never per campaign

§F's requirement, and the reason is concrete: a campaign may hold the Top 100
of one run **and** a #101+ school searched out of a later one. A single
`matchmaking_run_id` on `campaigns` would attribute the second to the first,
and nothing afterwards could detect it — the row would look exactly like the
ninety-nine beside it. The run is reached *through* the selection, so there is
no second copy of the run id to fall out of step. Proved by `F3`, which puts
two runs in one campaign and reads both back.

## 3. Selection → send, wired into both real paths

`assertSelectionMatchesSend` is extracted from A9.6's
`attachSelectionToSend`, and `recordDraft` carries the column **in its own
INSERT**.

**Not a second write, and that is the design.** A follow-up `UPDATE` would
leave a window in which a message exists without its cause — exactly what §S's
"send creation fails after selection" produces. `G3` asserts the atomicity: a
refused selection leaves **zero** rows.

Two writers would also have disagreed about re-drafting.
`attachSelectionToSend` refuses to re-point a message at a different selection,
which is right for a **sent** message and wrong for a **draft** being replaced
in place. So the draft-replacement `UPDATE` moves the selection with the body,
beside `programme_campaign_id`, which moves there for the same reason and
already did. That clause is unreachable once a message is `ACCEPTED`.

| path | selection comes from |
|---|---|
| `executionClaim` | `programme_campaigns`, via context — **never a caller** |
| `sendOutreach` | a caller parameter, **refused unless it checks out** |

The asymmetry is deliberate. `origin` is a claim about *who is acting*, which
an actor must not make about itself, so it lives in a second argument no
request body can reach. A selection id is a claim about an *existing row*: an
unverifiable one is refused rather than recorded, so it does not need to be
unreachable, only checked.

### The engine stays out of the send path

`outreachProvenance.js` no longer imports `serviceError` from
`matchmakingService.js`, which loads the frozen engine at module scope. Without
that change, `confirmSends.js` and `draftOutreach.js` — standalone CLI tools
that record mail an operator already sent by hand — would have loaded a scoring
engine.

`sendPathEngineIsolation.test.js` walks the real transitive import graph from
five entry points. Writing it found that the send path **already** reaches two
V2 modules, `athletePreferences.js` and `financialRules.js`, through
`server/db/entities/player.js`. That is the deliberate A7.9.2 coupling
`MAY_IMPORT_V2` admits by name, and both are leaf modules with **zero imports**
— asserted, so the exemption cannot become a door into the pipeline.

## 4. V2 campaign creation

`POST /api/players/:id/campaigns/from-matchmaking`. A **separate route**, not a
branch: `POST .../campaigns` is byte-identical and still reads
`players.recommendations`. Nothing switches at runtime, which is what makes the
rollback a matter of calling the other endpoint.

It reads and never scores. Every rank, band, Pursuit and layer comes out of
`matchmaking_programme_results` as the run stored it.

### What it deliberately cannot do

The schema's decision, not a policy invented here:

```
programme_campaigns.rank  NOT NULL   an unranked programme has no rank,
                                     and A9.5 refused to fabricate one
programme_campaigns.tier  NOT NULL   and tierForRank has NO BAND above 100
```

So a LIMITED_DATA programme, an unsupported association and a #431 school
cannot be campaign rows without inventing a rank, a tier, or both. They are
pursued through the **manual** path, which requires neither and which now
carries selection provenance — so their truthful status survives in
`matchmaking_selections` and their outreach is fully attributed. **Known
limitation**; widening the tier bands is an A9.8 decision about campaign
semantics, not a V2 one.

### A suppressed slot is not backfilled

V1 promotes the next programme from its `reserve` to keep the count at a
hundred. Doing that here would put #101 in as the hundredth row, and the
campaign's ranks would no longer be the run's ranks. **A campaign of 97 is the
truthful outcome of suppressing three.**

### Why it creates selections

§D asked for this to be deliberate. **Creating a V2 campaign *is* the selection
step**: the consultant's act is "pursue the top hundred of this run", and that
chooses exactly those hundred programmes at that moment. `source: TOP_100` is
the literally true answer to which surface they came from, and is what later
lets "did searched programmes out-reply ranked ones?" be asked at all. The
alternative is campaign targets with no provenance, which is the gap A9.6
existed to close.

## 6. Reply ingestion (§H)

**There is none.** No IMAP reader, no Gmail watch, no inbound webhook, no
provider callback. `contactIntelligence.js` has said so since it was written:
REPLY is *"OPERATOR-ASSERTED ONLY … Nothing ingests replies and nothing
classifies them."* `outreach_send_event.REPLY` has existed with no producer.

So A9.7 implements the bounded linkage that genuinely exists and invents no
Gmail behaviour:

| act | writes | says |
|---|---|---|
| `recordReply` | `outreach_send_event` | a reply **arrived** |
| `classifyReply` | `recruiting_observations` | what it **meant** |

`reply → send → selection → programme → run` resolves (`H1`), and resolves as
far as it honestly can for a V1 message — programme known, selection and run
`null` (`H2`).

**Rollout classification:** NON-BLOCKER for Stages 1–2, which are
consultant-operated and where a consultant reads their own inbox. **BLOCKER for
Stage 4.**

## 7. Classification workflow (§I, §J, §Z)

The caller names a **kind** and nothing else about the subject. The athlete,
programme, coach and selection are read from the message — there is no
parameter with which to file "Duke says the spot is gone" against a Clemson
pursuit. Manual by default; `AI_ASSISTED` is recordable with a version and
confidence, arrives `UNREVIEWED`, and is excluded from the reviewed projection
until a person confirms it. **Nothing in this build produces one.**

Four refusals, each a false record this could otherwise create:

| refused | because |
|---|---|
| classifying with **no reply recorded** | an operator working down a list could mark every unanswered message `NEGATIVE_REPLY`, and the data would hold refusals no coach made |
| a **call** without saying so | produces a classification with no REPLY event, which is true, and must be stated |
| an **athlete outcome** as a reply reading | "the athlete withdrew" is learned from the athlete; accepting it here is the §C collapse |
| `POSITION_FILLED` with no position | the claim says nothing without one |

## 8. Operator surface (§K)

One row per selection: the run's frozen numbers, what was sent, whether a reply
was recorded, and the latest **reviewed** reading. No rates, no funnel, no
aggregates.

`K5` proves the load-bearing property the way §L does: move the profile,
generate a second run, **assert the rank genuinely changed**, then assert the
older selection still reads its own.

The vocabulary is the careful part. `messages > 0, replies === 0` reads
**"Awaiting a reply"** and never "No interest" — nothing ingests replies, so a
zero is as much a statement about Thriv3's observation as about the coach. An
axis with nothing reviewed renders **nothing at all**, because "No reply yet"
fifty times down a list reads as a finding about fifty programmes.

## 13. Cold start (§P) — measured, and not implemented

On a 313 MB WAL-consistent copy of the live database:

| | |
|---|---|
| DB open + migrate | **52.3 ms** |
| engine module load | **27.3 ms** |
| **first `computeMatchmakingV2`** | **1,975 ms** |
| second / third / fourth | 38.2 / 31.9 / 32.1 ms |
| **a different athlete, same process** | **40.8 ms**, then 31.8 ms |

The context is cached **per sport, shared across athletes**, so the ~2 s is paid
**once per sport per process**. Startup and health checks are unaffected —
they pay 79 ms.

**Decision: do not warm on boot.** The benefit is one ~2 s wait per sport per
process, on an operator-initiated action that already renders a loading state.
Against it: ~4 s added before readiness for two sports, the corpus loaded into
every process including those that never serve matchmaking, and a new boot
failure mode. §P's own condition — "unless measured benefit is meaningful" — is
not met.

## 14. The finding that matters (§P / §Q)

**Any write invalidates the corpus digest cache, and the next staleness check
costs ~0.9 s.**

| | |
|---|---|
| `GET …/matchmaking/runs/current` | **9.3 ms** |
| …after **one** `tracking_events` INSERT | **929.9 ms** |
| …after another | **892.3 ms** |
| …with no write in between | **9.0 ms** |

**Mechanism.** `cachedCorpusDigests` keys on `corpusChangeToken(db)`, which is
`data_version:total_changes()`. `total_changes()` counts **every** write on the
connection since it opened — so a tracking pixel, an operator note, an
observation or a send record all invalidate a cache whose purpose is to avoid
re-digesting a 313 MB corpus.

**This is A9.4's design, not something A9.7 introduced.** A9.4 measured its
repair at 890 ms → 0.03 ms and that measurement was correct; what it did not
exercise was an **interleaved write**, which in production is continuous
because coaches open profiles and `tracking_events` records it.

It is a **performance** characteristic, not a correctness one: staleness is
computed correctly every time, and `P4` asserts the expensive recomputation
returns an identical digest.

Characterised in `corpusCacheInvalidation.test.js` rather than repaired here —
changing the corpus digest cache key is freeze-adjacent work, and A9.4's own
brief warned "never use the cheap token itself as historical corpus identity"
and "do not casually change corpus digest definition". **Recommended A9.8
repair:** key the cache on `data_version` plus a digest-input change counter,
or scope invalidation to the four tables the digest actually reads. This is the
one item standing between this branch and `A9_7_MERGE_READY`.

## 21. V1 rollback (§W)

Proved as a **walk**, not a diff. An athlete with no run, no selection and no
observation goes through the whole original workflow: V1 campaign creation
reads the stored analysis **file** and freezes twelve programmes with null
provenance; outreach is created with its `match_id` hint exactly as before; a
send is recorded, accepted, and reads back `PRE_PROVENANCE`.

**The mechanism, exactly:**

| | |
|---|---|
| per tab, per session | `?matching=v1` — no rebuild, no restart |
| per build | `VITE_MATCHMAKING_ENGINE=v1` |
| campaign creation | call `POST .../campaigns` instead of `.../campaigns/from-matchmaking` |
| neither | v2 |

The query parameter wins in **both** directions, so a build pinned to v1 can
still show one person v2. An unrecognised value falls through rather than
showing a blank screen. Nothing is deleted; `W5` asserts the two creation
routes are distinct handlers and that the V1 one does not mention the V2
service.

## 26. Three things that were wrong before they were right

**A SQL comment broke the file.** The draft-replacement `UPDATE` is a JS
template literal and carries its own warning — "No backticks in here" — which
my added comment immediately violated by naming two identifiers in backticks.

**Two existing guards fired and were obeyed rather than amended.** The
campaigns route "runs no SQL of its own", so the service resolves the athlete
itself, matching `createCampaign`'s signature. And the send-safety guard counts
routes matching `/send|execute|run|…/` — which the path `from-run` matched on
the substring **"run"**. Renamed to `from-matchmaking` rather than widening a
guard that exists to catch bulk send routes.

**The model marker had the wrong shape.** V1 writes
`matching_inputs.model` as an object — `{id, identifiedBy, criteria, note}` —
and the V2 path was writing a bare string, so a reader branching on `model.id`
would have got `undefined` for every V2 campaign. Found by the rollback test.

**Stage 2 — a small real cohort.** **5–8 athletes**, one or two consultants,
V2 by default with `?matching=v1` available on every screen.

| | |
|---|---|
| monitor | Matchmaking load time (the §14 regression), selection → send provenance coverage, refusal rates by code, V1 fallback usage |
| inspect | `selections/overview` per athlete; every `PRE_PROVENANCE` V2-originated send is a wiring bug |
| collect | where a consultant disagreed with a band, where LIMITED_DATA was unhelpful, where the #101+ manual path was needed |
| rollback triggers | any `FREEZE_VIOLATION`; any send with the wrong programme; Matchmaking load > 3 s; a consultant needing V1 to do their job |

**Do not tune V2 during the cohort because an individual rank looks surprising.**
A8.1 §M already recorded that as NOT_A_BLOCKER, and the freeze names the three
classes of evidence that would justify a change. Collect, do not adjust.

**Stage 3 — comparison and outcome collection.** Run V1 and V2 side by side for
the same athletes. Begin populating the §S analytics dataset. Still no tuning.

**Stage 4 — V2 default.** Requires automated reply ingestion (limitation 2) and
a retention policy (limitation 5).

**Stage 5 — V1 retirement.** Only once outcome data can answer whether V2 ranked
better, which needs a full recruiting cycle. Not before.

### Why the verdict is not `A9_7_MERGE_READY`

Every gate passes and the branch is safe, reversible and fully guarded. But
§14 is a measured, user-facing defect found at this gate and deliberately not
fixed: merged and deployed, the Matchmaking screen would take ~0.9 s instead of
9 ms whenever any write has occurred — which, with coaches opening profiles, is
continuously. Recommending a merge while knowing that would not be honest.

**One change flips this to `A9_7_MERGE_READY`:** repair the corpus digest cache
key so unrelated writes do not invalidate it, and re-measure
`runs/current` under interleaved writes. Nothing else on this list is a
precondition for merging; the rest are rollout-stage preconditions.
