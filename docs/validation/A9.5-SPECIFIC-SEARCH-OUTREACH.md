## 1. The old Specific Search, traced

| | |
|---|---|
| entry | a toggle on the V1 Matching tab |
| search | `GET /api/colleges/search` — the registry, by name, per sport |
| selection | the operator picks a returned row; **nothing resolves text to a school** |
| storage | `athlete_programmes`, upserted on `(athlete_id, college_name, sport)` |
| outreach | `ManualOutreachDialog`, addressed by the relationship id |

It was already careful about the thing that matters most: there is no fuzzy
matcher anywhere in it. `server/lib/schoolMatch.js` records why — the matcher
that *did* answer when unsure published Belmont Abbey's domain for Belmont and
gave Kansas the academic rating of Central Arkansas.

**What it could not do** is say where a school sits. "Adding Stanford records
that the athlete asked for Stanford. It does not rank Stanford" — so the
question a consultant is actually asked on the phone had no answer anywhere in
the product.

### Where `Top100 == the universe` was assumed

| site | assumption |
|---|---|
| `createCampaign` | reads `players.recommendations` — **the V1 analysis file** |
| `visibleTop100` | derives the actionable hundred from that blob + a 101–150 reserve |
| `programme_campaigns.rank` / `.match_score` | **`NOT NULL`** |

The last one is the live constraint: an unranked programme cannot enter a
campaign without a fabricated number, which §M forbids.

## 2. The new contract

> **Specific Search finds a programme and shows where it sits in this
> athlete's existing V2 universe. It never runs a model for one school.**

That is arithmetic, not taste. A rank is a **position in a population** —
"#431 of 824" means nothing except relative to the other 823 — so a
single-programme evaluation would produce a number with no denominator, and
whatever number it produced could disagree with the Matchmaking list about the
same school. That is the point at which a consultant stops trusting both.

```
registry search (unchanged)  ->  operator picks a row
  -> GET /players/:id/matchmaking/programme?name=…&runId=…
  -> programmeResult(runId, {collegeName, sport})      [A9.2, already existed]
  -> standing rendered from the SAME view model the result list uses
```

Identity is the registry row's own `name`, matched **exactly** against the
run's stored `college_name`. No new matcher, no fuzzy join.

### Three thin reads and one write

| route | payload | measured |
|---|---|---|
| `GET …/matchmaking/programme` | **0.6 KB** | 7–27 ms |
| `GET …/matchmaking/top` | 15.2 KB | 6.2 ms |
| `GET …/matchmaking/selections` | 0.8 KB | 5.1 ms |
| `GET …/runs/current` (for comparison) | 556 KB | 13.2 ms |

A lookup is ~1,000× smaller than the run it reads from.

## 3. No run, and stale runs

**No run** (§E) — the empty state says it, rather than letting someone open a
search box that cannot answer:

> *"Looking up a specific school also needs a run: a programme's rank only has
> meaning inside the full universe it was ranked against."*

`lookupProgramme` throws `RUN_NOT_FOUND` and scores nothing. `S7` asserts no
run is created by the attempt.

**Stale run** (§F, §Q) — the historical run is still inspectable, and says so:

> *"These matches are outdated… anything recorded now is recorded against that
> older ranking."*

Selection is **not** forbidden. A consultant mid-conversation about Tuesday's
list is acting on what they were shown, and that is exactly what the provenance
record is for. What must not happen is them doing it unknowingly, or the record
being re-pointed at a newer run afterwards.

The lookup is scoped to the run **on screen** — `runId` is passed explicitly
rather than letting the server pick the current one, so a standing can never
come from a newer run than the list being read. Mutation-tested.

## 5. Outreach provenance

A new append-only ledger, `matchmaking_selections`. One row per act of choosing
a programme out of a specific run.

### Why a ledger and not a column on `athlete_programmes`

That table is an **upsert** keyed on `(athlete_id, college_name, sport)` — one
mutable row per programme. An operator who selected Lindenwood from Tuesday's
run and again from Friday's would have Tuesday's provenance overwritten, and
the record of what they actually acted on would be gone. §Q forbids exactly
that. Append-only makes it impossible: a second selection is a second row.

### Why not on `programme_campaigns`

Inspected first, as §J requires, and the answer is in `createCampaign`: it
reads `players.recommendations`, the **V1 analysis file**, and freezes its own
rank, `match_score` and breakdown. **There is no V2-originated path into a
campaign today**, so a `matchmaking_run_id` column there would have no writer —
speculative schema that reads as a promise the code does not keep. When
campaign creation moves onto persisted runs, it carries the run id from the
selection, and that phase adds the column.

`S9` and `S10` assert both tables are untouched.

### What is recorded

`status`, `rank`, `band` and `pursuit` are snapshotted from the run —
redundancy, not drift, because the run is immutable — plus `source`
(`TOP_100` / `SPECIFIC_SEARCH` / `FULL_UNIVERSE`) and `run_was_stale`.

**`rank` and `band` are nullable, and that is the point.** Verified live:

| programme | status | rank | band | pursuit |
|---|---|---|---|---|
| Princeton | `RANKED` | 4 | `PRIORITY_OUTREACH` | 0.635325 |
| Garden City Community | `UNSUPPORTED_ASSOCIATION` | **null** | **null** | **null** |

No fabricated rank, no zero standing in for one. A zero would read as "ranked
last"; `W3` asserts against both.

## 6. Validating run ↔ programme — §K

Four things are established before a row is written:

1. the run exists
2. the run **belongs to this athlete**
3. the programme is **in that run**
4. the identity stored is the **run's** spelling, not the caller's

(4) matters as much as the rest: a caller passing "Lindenwood University" for a
run holding "Lindenwood" would write a row that never joins back. The lookup is
the authority and its row is copied.

A `TOP_100`-labelled selection is additionally checked to actually be in the
top 100 — a row labelled `TOP_100` carrying rank 431 would make the first "do
Top 100 selections out-perform searched ones" comparison meaningless.

A run with selections against it **cannot be deleted** (`ON DELETE RESTRICT`).

## 7. Duplicates — §R

`athlete_programmes`' existing `UNIQUE (athlete_id, college_name, sport)` already
makes a duplicate outreach *target* impossible whichever UI path created it.
The selections ledger is deliberately **not** deduplicated: two selections of
the same programme from two runs are two different facts, and collapsing them
would destroy the provenance of the first. `W10` asserts both halves.

## 8. The email boundary — §N, §O

**No V2 data reaches the email path, and A9.5 adds no adapter.** The one
"pursuit" hit in the outreach code is `sequenceStrategy.js` using the word for
cadence — a naming collision, not a leak.

The major gate was already positive-only by construction:

```js
const intendedMajorLabel = majorLabel && (college.notable_majors || []).includes(majorLabel)
  ? majorLabel : '';
```

A membership test with **no negative branch**. Absence produces an empty string
and no clause. `offers_intended_major` is deliberately absent from
`TEMPLATE_VARIABLES`, so no saved template can branch on it.

Nine tests pin this where it currently holds by construction — because the
construction is one careless `else` away from not holding.

> **A test that proved nothing, caught:** `O5` originally read
> `TEMPLATE_VARIABLES.map(v => v.name ?? v)`, and the key is `token`. It was
> comparing objects, so `not.toContain('offers_intended_major')` passed no
> matter what the list held.

> **A check that was too blunt, corrected:** banning the substring `score` in
> template tokens matched `player_sat_score` and `player_act_score` — the
> **athlete's own** test results, which legitimately belong in a recruiting
> email. The boundary is Thriv3's internal numbers, so the list now names them,
> and the test asserts the athlete-owned tokens are still present.

## 9. The workspace header — §P

Under V2 the header button **navigates**. It does not compute.

`handleAnalyze` runs the V1 analysis in the browser, uploads a file and
repoints `players.recommendations`. Leaving it as the most prominent control on
a V2 screen meant the obvious button silently ran the **old engine** and
overwrote V1's stored answer, while the tab below showed a V2 run the click had
not touched — two engines, one button, no way to tell which had answered.

Under `?matching=v1` it is byte-for-byte the previous control, calling the same
handler, still on the context for the V1 tab that uses it.

## 12. Future telemetry — §T

The ledger supports A9.6 recording `sent` / `opened` / `replied` /
classification / timing against `(matchmaking_run_id, college_name, sport)`.
What A9.6 still needs:

1. **A join from an outreach action to a selection.** `outreach` keys on
   `(athlete_id, coach_id)` and has no programme column; the path today is
   coach → school. Either a `selection_id` on the outreach row, or a resolved
   view.
2. **`programme_campaigns.matchmaking_run_id`**, once campaign creation reads
   persisted runs.
3. **Reply classification** is not in this schema at all.

Keep **ATHLETE→PROGRAMME FIT** (this engine's output) separate from
**PROGRAMME→ATHLETE INTEREST** (what a coach then did). They are different
measurements and a single "score" column would merge them irreversibly.

## 15. Privacy

The selections ledger holds programme identity and engine facts. No contact
details, no coach data, no athlete PII. The lookup response carries one
programme and the run's counts — no input snapshot, no digests. `SS12` asserts
no internal machinery reaches the standing surface.
