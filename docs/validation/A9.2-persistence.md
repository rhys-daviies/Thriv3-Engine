## Current persistence architecture

SQLite. `schema.sql` creates tables with `CREATE TABLE IF NOT EXISTS`;
`migrate.js` owns every column added to an existing table. Both run on each
boot and are idempotent.

**V1's answer is a file pointer.** `players.recommendations` holds a path into
`server/uploads/`, not JSON — 3 of 4 players on the working database have one.
Re-analysing overwrites it and saving a profile nulls it.

That is why V2 must coexist rather than overwrite, and the repository already
made this decision once: `programme_campaigns` **copies** rank, score and
breakdown rather than pointing at the mutable blob, "which is what makes a
campaign from last season still readable after the model has been retuned
twice". A9.2 follows that precedent.

Two other conventions followed exactly: athlete-owned tables declare
`REFERENCES players(id) ON DELETE CASCADE` because the delete path issues a
bare DELETE; and **programme identity is snapshotted as `(college_name,
sport)`, never a foreign key to `colleges`**, because a programme is retired by
`active = 0` and renamed in place.

## What is persisted, recomputed, and never stored

| | |
|---|---|
| **MUST PERSIST** | run identity (matcher, engine freeze, corpus digest, computedAt, both schema versions, sport); the athlete input snapshot; per programme: identity, status, rank, Pursuit + grade, each layer's value, grade, coverage and refusal reason |
| **MAY RECOMPUTE** | ranking band (`bandForRank(rank)`); layer state (SCOREABLE exactly when the value is non-null); `missingLayers`; explanation prose |
| **MUST NOT PERSIST** | coach emails, athlete contact details, guardian or club-coach fields, the whole player row, engine `basis` blocks, weights, shares, midranks, paths |

Explanation prose is derived, not stored, because persisting sentences freezes
a *rendering* rather than a fact — and A8.2 is the worked example: the engine's
answer changed and every sentence had to change with it.

## Athlete input snapshot

20 fields, each one read by a layer or a preference: sport, ability, position,
entry year, the three contribution fields, geography, academics, intended
major, the three priorities, criterion ranking, recruit type.

Not the player row. A historical run must stay interpretable after the athlete
changes, but snapshotting everything would put guardian email and club-coach
email into permanent storage for no ranking purpose. `inputDigest` is computed
over a fixed key order so it cannot depend on insertion order.

## Storage tournament — measured, not argued

One run, men's, 1,205 programmes:

| shape | per run | queryable |
|---|---|---|
| A. one JSON blob | 682 KB (61 KB gzipped) | **no** — one programme needs the whole blob parsed |
| B. normalized, full columns | 334 KB | yes |
| B. normalized, lean columns | 268 KB | yes |
| C. **chosen: normalized facts + bounded JSON snapshot** | **406 KB** incl. indexes | yes |

Normalized is **half the size of the raw blob and queryable** — there was no
trade-off to make.

Measured by page allocation on a real-database copy, the final shape costs
**406 KB/run** men's, and `dbstat` showed where it goes: 238 KB data, 272 KB
indexes before trimming. **Indexes cost more than the data.**

So one index was removed, on evidence: `(run_id, college_id)` cost **109 KB per
run — 21% of the table** — to make a programme lookup 0.034 ms instead of
0.082 ms. The primary key already indexes `(run_id, college_name, sport)`,
which is the programme identity `athlete_programmes` and `programme_campaigns`
both use. 514 → 406 KB/run.

*(Three measurement methods disagreed: file-size delta said 84 KB/run because
the 298 MB database had free pages from an earlier DELETE. Page allocation
after VACUUM is the honest number.)*

## Schema

`matchmaking_runs` (17 columns) — identity, both schema versions, sport, input
snapshot, counts, contribution state. `matchmaking_programme_results` (21
columns) — snapshotted programme identity, status, rank, Pursuit + grade, and
each layer's value, grade, coverage and reason.

`PRIMARY KEY (run_id, college_name, sport)`;
`idx_matchmaking_runs_player (player_id, computed_at DESC)`;
`idx_matchmaking_results_rank (run_id, rank)`.

A refusal is stored as **NULL, never 0** — a zero would sort as "worst" to any
consumer that forgot to check `status`. A CHECK constraint pins the three
statuses.

## Precision

Scores are `REAL` (IEEE-754 double) and the adapter already rounds to 6 dp, so
storage round-trips exactly — verified with `Object.is` on every ranked row, and
ordering re-checked after reading back, because a rounding that changed order
would be invisible to a value comparison.

## Immutability and the current run

Nothing is ever updated. Recomputing writes a **new** run; the old one keeps
the ranks it had, verified by rebuilding a run's digest after the athlete's
rating changed from 6 to 9.

The current run is **the latest one, queried** — not a pointer and not a flag.
A pointer column is exactly what V1 has, and the reason a campaign can be one
profile save away from losing its Top 100. A flag needs two writes to move and
has a window where a player has none or two. The latest immutable run has
neither: nothing updates, so nothing can tear, and rollback is "ignore the
newer run".

## API

`POST /api/players/:id/matchmaking` → 201 with `runId` + the full result.
`GET …/matchmaking/runs/current` → the persisted run plus `staleness`.
`GET /api/matchmaking/runs/:runId` → one immutable run.

GET never writes — proven by a test that counts rows before and after.

**No deduplication, deliberately.** A POST is somebody asking for a
recomputation, and recording that they asked is the point of an immutable run.
"Identical" is not free to establish either — it means comparing 1,205
programme rows. The cheaper and truer answer is `staleness` on the current-run
GET, so a UI can decline to ask rather than ask and be silently deduplicated.

## Transactional integrity

Run metadata, input snapshot and all programme rows are **one transaction**. A
test poisons the 11th programme row with an illegal status: the write throws
and leaves **zero** rows in either table — not a run with 10 programmes, which
would be indistinguishable from a real one with a small universe.

## Staleness

`PLAYER_INPUT_CHANGED` · `CORPUS_CHANGED` · `ENGINE_CHANGED`, reported
together rather than as one boolean, because they mean different things: an
operator's own edit, new evidence arriving, and a freeze that moved.

Nothing recomputes and nothing is deleted. `ENGINE_CHANGED` is false under the
current freeze by construction, and a simulated different freeze makes it true.

## Future compatibility

**Specific Search (A9.5):** `programmeResult(db, runId, { collegeName, sport })`
returns a historical rank, status and layers without recomputing — which it
could not do anyway, since the corpus has moved on. A test asserts a programme
keeps its #1 after the athlete's rating drops.

**Outreach (A9.6):** an outreach event needs two columns to become
attributable — `matchmaking_run_id` referencing `matchmaking_runs(id)` and the
programme's `college_name` + `sport`. Then "this school was contacted when
Thriv3 ranked it #37 under run X" is a join, not an archaeology exercise.
Nothing in campaigns is changed here.
