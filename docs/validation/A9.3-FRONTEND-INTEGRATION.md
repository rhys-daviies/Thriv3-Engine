byte-identical to its pre-phase state. **Verdict: `A9_3_FRONTEND_READY`.**

## 1. The old flow, before anything was changed

The V1 journey is **client-side and pointer-based**, and that is what forced
every decision here:

1. `PlayerWorkspace` loads the athlete, reads `players.recommendations` — a
   **file URL** into `server/uploads/` — and fetches that JSON.
2. **Find Matches** (in the workspace header, not the tab) runs `analyze()` in
   the browser, uploads the result as a file, and repoints
   `players.recommendations` at it.
3. `MatchingTab` renders `actionableRecommendations` — the Top 100 minus what
   the operator removed, topped up from a 101–150 reserve — twenty per page.

Two properties of that flow matter. The answer is a **file**, so there is one
of them and recomputing destroys the previous one; and the computation happens
**in the browser**, so nothing server-side has a record that it happened.

## 2. The new flow

`GET /api/players/:id/matchmaking/runs/current` on load. That is all. No
recomputation, ever, without an operator asking.

| state | screen |
|---|---|
| no run | intentional empty state, one **Generate matches** button |
| current run | run bar (Current) · preferences · results |
| stale run | **the historical results stay rendered**, with the reasons above them and **Refresh matches** |
| 409 | contribution blocking state with a route to Edit Profile |

Refresh `POST`s a new immutable run and switches to it. The old run is never
touched — proven below against the database, not merely asserted.

### Why persisted-first

A9.2 made runs immutable so that what Thriv3 told a consultant on Tuesday is
still readable on Friday. A screen that silently recomputed on load would leave
that record intact and quietly stop showing it, which is the same outcome as
not having it. Rankings would also move under a consultant mid-conversation:
the corpus changed 1,042 cells during A9.2 alone, from one routine 7B
promotion.

## 3. Component architecture

```
src/lib/matchmakingV2View.js      pure view model + the wording boundary
src/lib/useMatchmakingV2.js       the adapter: run, staleness, generate, refresh
src/lib/matchmakingVersion.js     the rollback switch
src/api/client.js                 + `matchmaking` (3 calls)

src/pages/player/MatchingTabSwitch.jsx          the ONE branch point
src/components/matchmaking/MatchmakingV2Panel.jsx    states
                           MatchmakingRunBar.jsx     when · current/outdated
                           MatchmakingPreferences.jsx major + priorities
                           MatchmakingResults.jsx     scope + paging
                           MatchmakingResultCard.jsx  one programme
```

No component imports the API client or branches on an HTTP status.

### The normaliser exists because two shapes reach this screen

`POST` answers with the **live** service result; `GET …/runs/current` answers
with the **persisted** one. They agree about every engine fact and differ in
one presentational extra: an unscoreable layer carries `missing:
['playingPathway']` live, and does not when persisted. A9.2's parity is over
`resultDigest`, which covers ids, status, rank, pursuit, the three values and
the three reasons — not `missing`.

A screen reading `missing` straight off a response would show a line of detail
immediately after Refresh that **vanished on the next page load**. So the view
model is cut to the persisted contract and `missing` is dropped rather than
shown-when-present. A test asserts the two shapes normalise to identical
objects.

## 4. Result hierarchy, bands and scores

Band first, rank second, score third.

| band | range | chip |
|---|---|---|
| PRIORITY_OUTREACH | 1–25 | Priority outreach · green |
| STRONG_PURSUIT | 26–50 | Strong pursuit · blue |
| VIABLE_CONSIDERATION | 51–100 | Viable consideration · purple |
| BROADER_UNIVERSE | 101+ | Broader universe · muted |

Every chip prints its **label and its rank range**, so the band survives
monochrome, a screen reader and a printout. Colour is never the only signal.

**Pursuit is a whole number out of 100, and that is a truth claim.** A8
measured that hundreds of adjacent ranks differ by less than 0.001. The live
run makes the point by itself: ranks #2, #3 and #4 all display **64**, and the
card says so — *"Scores are rounded, so programmes close together in the list
can show the same number. The ranking order is exact."* Stored values are
untouched and nothing re-sorts on the rounded number.

## 5. Full universe

`Top 100 | Full universe`. Top 100 is the **prefix of the one ordering**
(`rank <= 100`, mirroring `topSlice()` on the server), not a second list and
not a second model.

The full universe is 1,205 programmes over 61 pages. **V1's pager cannot
address it** — it renders `min(totalPages, 5)` buttons, which is exactly right
for V1's 100 recommendations and would leave pages 6–61 unreachable here. So
V2 has its own windowed pager (`Previous · 1 … 59 60 61 · Next`) rather than an
edit to V1's.

## 6. The two non-ranked states

Both sentences are about **Thriv3**, never about the school.

| | LIMITED_DATA | UNSUPPORTED |
|---|---|---|
| chip | Not enough evidence to rank (amber) | Association not modelled (muted) |
| rule | amber left border | grey left border |
| says | "Thriv3 matches this association but does not hold enough evidence to rank this programme for this athlete." | "Thriv3 does not yet hold the eligibility rules required to rank this association." |
| and | "a gap in Thriv3's data, not a judgement about the programme" | "**The athlete can attend these institutions.** Thriv3 simply cannot place them in a ranking yet." |

Neither carries a band. Expanding either shows the engine's own refusal phrase
per layer.

## 7. The major, and the language boundary

The chip reads **Major preference: exercise science** and is read-only — A9.4
owns editing, and a removal affordance that did nothing would be worse than
none.

A8.2 established `notable_majors` is **partial positive evidence**: 321 of 349
D1 women's programmes omit Mathematics, Penn State and Ohio State among them.
Absence establishes nothing, so the engine refuses rather than scoring zero.

Three things keep that out of the UI:

1. **Structural.** `majorFit` is a non-required preference component inside
   Opportunity, so `combine()` never propagates its reason to the layer. Over a
   real 1,205-programme run, `MAJOR_NOT_IN_PARTIAL_EVIDENCE` appears **zero**
   times as a persisted layer reason. The screen cannot make a per-programme
   major claim because the data to make one is not there.
2. **Imported, not copied.** Refusal phrases come from
   `shared/matching/v2/explain/vocabulary.js`. A frontend copy is how "does not
   offer" comes back; the import makes the phrase unforgeable. This required
   adding `matchmakingV2View.js` to `MAY_IMPORT_V2` — see §11.
3. **Tested twice.** A walk over every exported string of the view model, and a
   render of all three states including a synthetic
   `MAJOR_NOT_IN_PARTIAL_EVIDENCE` programme, against eight banned spellings.
   Both were mutation-checked.

## 8. Staleness

| code | sentence |
|---|---|
| PLAYER_INPUT_CHANGED | The athlete's profile changed after these matches were generated. |
| CORPUS_CHANGED | Thriv3's recruiting data has been updated since these matches were generated. |
| ENGINE_CHANGED | The matcher has been updated since these matches were generated. |

Several may hold at once; all are listed. No digest, SHA or schema version
reaches the UI — `runView` does not even carry them, so the bar cannot leak one
by accident. An unrecognised code is dropped rather than printed raw.

Proven live: setting `academic_strength_priority` on the copy flipped the run
to **Outdated** with the profile sentence, results still on screen. Refresh
then produced a genuinely different ranking — **Princeton to #1** once academic
strength became "extremely important".

## 9. Contribution — 409

Not an error. `familyContribution()` returns null to mean REFUSE; financial
viability is 20% of Pursuit with a gate beneath it, and assuming $0 would make
every expensive programme look unaffordable on an assumption nobody made.

Exercised against a **real athlete** — Ryan Billings, `budget_range
Undeclared` — who genuinely returns 409 in production. The screen shows the
blocking state and a route to Edit Profile, computes no partial ranking, and
**persisted nothing**: that athlete has zero rows in `matchmaking_runs`.

With a run already loaded, the 409 is reported *beside* the results rather than
replacing them.

## 10. Loading, errors, and what survives them

Eight states, told apart: loading · generating · refreshing · no run · 409 ·
404 player · 422 profile · 500 · network.

Branching is on the server's **`code`**, not the status, because
`PLAYER_NOT_FOUND` and `RUN_NOT_FOUND` are both 404s and mean opposite things —
one offers a Generate button and the other must not.

**Results already on screen survive everything.** A refresh dims them and sets
`aria-busy`; it never unmounts them. A refresh that fails leaves the run
exactly where it was. Both are mutation-tested: clearing `run` during a refresh
fails three tests.

## 11. V1 coexistence and rollback

The switch is at the **route**, in `MatchingTabSwitch.jsx`, so
`MatchingTab.jsx` is untouched. That is deliberate: a switch inside it would
default a dozen V1 suites onto V2 and they would have to be edited to keep
asserting what they already prove — which is how "V1 is unchanged" stops being
checkable.

```
?matching=v1                 this tab, this session. No rebuild.
VITE_MATCHMAKING_ENGINE=v1   the default for a whole build.
neither                      v2.
```

The query parameter wins, because a build pinned either way must still let one
person check the other. An unrecognised value falls through to the default
rather than blanking the screen.

**Specific Schools is not rebuilt and is not lost**: the V2 screen keeps one
control pointing at the V1 view that still has it. A9.5 owns bringing it onto
the run.

`importGraph.test.js`'s `MAY_IMPORT_V2` gained two entries (the view model and
its test), following that file's own stated protocol — deliberately, dated, with
the reason. The precedent is exact: `contributionIntake.js` and
`preferenceIntake.js` already import V2 *vocabulary and validators, never
scorers*, for the same reason a second copy drifts.

## 12. Performance, measured

Rendering, on the real 712KB / 1,205-programme payload (jsdom):

| | |
|---|---|
| normalise the whole run | **1.1ms** |
| initial Top 100 render | **28.8ms** (20 cards) |
| switch to Full universe | **7.3ms** |
| jump to page 61 | **4.3ms** |
| scope filter over 1,205 | **0.078ms** |
| **mount all 1,205 cards** | **310.8ms** |

The whole run stays in state; one page of twenty is mounted. The last row is
why — 11× the cost in jsdom, before a browser does layout and paint. No
horizontal overflow at 375px; 20 cards mounted on mobile.

### A measured defect in A9.2's route, not in this frontend

Opening the tab costs **~880ms**, and almost none of it is the payload:

| request | payload | time |
|---|---|---|
| `GET /matchmaking/runs/:id` (no staleness) | 570KB | **15.9ms** |
| `GET …/runs/current` (same payload + staleness) | 570KB | **880ms** |

Isolated server-side:

| | |
|---|---|
| `readRun` — 1,205 rows → payload | **7.7ms** |
| `runStaleness` — whole check | **1,064ms** |
| ↳ `corpusDigests` alone | **896ms** |
| `runStaleness` again (no cache) | **877ms** |

**Serving the answer is 15.9ms; asking whether it is still fresh costs 55× that,
on every load.** A9.1 hit this exact cost on the compute path and solved it with
a two-level cache — `corpusChangeToken` (SQLite `data_version`, ~0.01ms) gating
the digest. `runStaleness` never got that treatment, because until A9.3 nothing
called it outside a test.

Not fixed here: this phase is scoped away from backend changes, and a cache on
the staleness path deserves its own measurement and tests rather than being
slipped into a frontend commit. **It is the first item for A9.4.** Nothing about
it is wrong — the answer is correct, it is just recomputed from scratch each
time.

## 13. Accessibility

Bands carry words and ranges, never colour alone. Disclosures are real
`<button type="button">` with `aria-expanded` and `aria-controls` (the shared
`Disclosure`, reused rather than hand-rolled). Loading is `role="status"
aria-live="polite"`. Refreshing results are `aria-busy`. The scope switch is a
`role="tablist"` with `aria-selected`; the pager is a `<nav aria-label>` with
`aria-current="page"`. Both non-ranked states are textual.

## 14. Privacy

The view model carries no `inputSnapshot`, no engine freeze, no corpus digest
and no schema version — asserted by test. A result surface renders no `@`, no
guardian, no phone, no player id and no run id. `scan:committed-pii` clean;
`snapshot:pi --check` 0 differences.
