## 1. Root cause

`cachedCorpusDigests` and `poolContextFor` both gated on
`corpusChangeToken`, which is `data_version:total_changes()`.
**`total_changes()` counts every write on the connection since it was opened**,
so a tracking pixel invalidated a cache whose only purpose is to avoid
re-hashing ~350,000 rows.

Reproduced at `04efbb4` on a WAL-consistent 313 MB copy of the live database,
before anything was changed:

| | |
|---|---|
| `GET …/matchmaking/runs/current`, warm | **9.6 ms** |
| …after ONE `tracking_events` INSERT | **895.2 ms** |
| …after another | **908.3 ms** |
| …warm again | 13.8 ms |
| authoritative digest recomputations | **2** |

The digest was recomputed and came back **identical** both times. The cost was
real; the information gained was nil.

## 3. Why an application-level counter was rejected

§G asked for every writer to the three tables. There is **no single service**
through which corpus writes flow:

| table | writers found |
|---|---|
| `colleges` | `loadMatchingInputs`, `seedRosterGapColleges`, `loadAcademicRatings`, `applyWomensProgrammes`, `applyPhase6BProgrammeRepairs`, `applyUscaaDivision`, `seedTestPool`, `migrate` |
| `roster_players` | `projectRosterMinutes`, `alignRosterSchoolNames`, `applyClassYearReacquisition`, `applyContaminationRemoval`, `applyReacquiredRosters`, `poolBenchmarkAudit`, `refreshGraduationYears`, `applyUscaaDivision`, `seedTestPool` |
| `recruiting_arrivals` | `buildRecruitingHistory`, `seedTestPool` |

Roughly fifteen standalone scripts, each its own process, plus `migrate.js` and
the test seeder. An increment placed in application code would have to be added
to every one, and **the next script anybody writes would silently not have it**.
That is a false-negative generator, and a false negative serves a corpus
identity that has already moved.

A trigger cannot be forgotten. It fires for a script, a migration, a test, or
somebody typing SQL into a shell.

## 4. Design tournament

| | false negatives | false positives | all writers | cross-process | cost | verdict |
|---|---|---|---|---|---|---|
| **A.** `total_changes()` (current) | DDL only | **every write anywhere** | yes | partial | 0.007 ms | the defect |
| **B.** row counts / max markers | **YES — an UPDATE that changes neither is invisible**; `colleges` has no update marker | few | yes | yes | ~tens of ms (index scans) | **rejected** |
| **C.** application revision table | **YES — ~15 scripts, and the next one** | none | **no** | yes | trivial | **rejected** |
| **D.** triggers → bounded revision row | DDL only, and `schema_version` covers it | only genuine corpus writes | **yes, unconditionally** | yes | 0.010 ms | **chosen** |
| **E.** existing repo mechanism | — | — | — | — | — | none exists |

B is rejected on the one criterion §D says is non-negotiable. C is rejected on
the evidence in §3.

## 5. The chosen mechanism

```sql
CREATE TABLE corpus_revision (
  id       INTEGER PRIMARY KEY CHECK (id = 1),
  revision INTEGER NOT NULL DEFAULT 0
);
```

Nine triggers — three tables × INSERT/UPDATE/DELETE — each doing
`UPDATE corpus_revision SET revision = revision + 1 WHERE id = 1`.

**One row, for ever.** `CHECK (id = 1)` makes §H's bounded-state requirement a
database guarantee rather than a convention; a revision *log* would grow by one
row per imported roster row.

### The token is `schema_version:revision`

Each half closes a hole the other cannot, and both were measured rather than
assumed:

| | moves on |
|---|---|
| `schema_version` | **DDL, from any connection, and nothing else.** An `ALTER TABLE` on another connection moved it; inserts on either connection did not. |
| `revision` | INSERT / UPDATE / DELETE on the three corpus tables, from any connection, process or statement, inside the writer's own transaction. |

`schema_version` catches a migration rewriting one of the three tables in
place — something **`total_changes()` has never caught**, because DDL changes
no rows. So the new detector is strictly more complete than the old one, not
merely more precise.

### Why not `data_version`

It moves when another connection commits **anything**. A worker process writing
a tracking event would invalidate the server's cache — the A9.7 defect
relocated to a second process rather than fixed. `E2` asserts the new detector
does not do this.

### Table-level, not column-level

The digest hashes a **subset** of each table's columns, but `buildPoolContext`'s
market join also reads `roster_players.id` and
`recruiting_arrivals.roster_row_id`, which the digest does not hash. A
column-scoped trigger would miss a write to those. Invalidating on any write to
these tables is strictly safer and costs only an occasional
confirmed-identical recomputation.

### Fail-safe

A database without the table, without all nine triggers, or with the row
deleted falls back to the broad `corpusChangeToken` **for that connection's
whole life** — slower, and correct. Probed once per connection, not per call.

This matters because the alternative failure is silent: a missing row makes
`SELECT revision` return `undefined`, which formats into a *stable* token and
is indistinguishable from "nothing has changed". `K3` and `K4` assert the
fallback; mutation **M3** demonstrates it degrading rather than lying.

## 6. Why false negatives are prevented

| route a relevant write could take | caught by |
|---|---|
| any application service | trigger |
| any of ~15 import/repair scripts | trigger |
| `migrate.js` | trigger — measured, 28 `colleges` UPDATEs per pass |
| a test utility or seeder | trigger |
| hand-typed SQL in a shell | trigger |
| another process entirely | trigger (the revision is DB state, read committed) |
| DDL rewriting a corpus table | `schema_version` |
| the machinery itself being absent or damaged | fallback to the broad token |

## 7. Multi-connection and multi-process (§E)

| | |
|---|---|
| `E1` | a relevant write on **another connection** is seen by this one |
| `E2` | an **irrelevant** write on another connection does **not** invalidate |
| `E3` | a **reopened** connection reads the same revision — it is database state, not connection state. `total_changes()` resets on open and could not do this, which is the connection-local trap A9.4 recorded. |
| `E4` | two different databases sitting at the **same revision value** are never confused — the per-connection `WeakMap` keying from A9.4 is preserved, and the test asserts the collision premise before relying on it |

## 8. Transactions (§F)

| | |
|---|---|
| `F1` | a **committed** relevant write moves the revision |
| `F2` | a **rolled-back** relevant write leaves it exactly where it was, and the row is gone |
| `F3` | a rolled-back irrelevant write also leaves it alone |

The trigger runs inside the writer's transaction, so this is structural rather
than arranged.

## 9. Invalidation matrix (§J)

**Irrelevant — token unchanged.** Each case also asserts that the **old** token

`tracking_events` · `recruiting_observations` · `matchmaking_runs` · `coaches` ·
`players` · `campaigns`

`J1`: one hundred consecutive irrelevant writes cost **one** recomputation (the

**Relevant — token always moves.** All nine combinations:

| | INSERT | UPDATE | DELETE |
|---|---|---|---|
| `colleges` | ✓ | ✓ | ✓ |
| `roster_players` | ✓ | ✓ | ✓ |
| `recruiting_arrivals` | ✓ | ✓ | ✓ |

`J2`: a **no-op** DELETE matching zero rows correctly does *not* invalidate —

the relevant one.

## 10. Digest correctness (§K)

`K1` runs six relevant mutations and asserts `cachedCorpusDigests` equals a
fresh uncached `corpusDigests` after every one, for both universes.

`K2` is §C's third case, and the one a naive detector gets wrong in the
dangerous direction: an UPDATE writing the value already present **does**
recompute, and the authoritative identity comes back unchanged.

### Mutations

| mutation | result |
|---|---|
| detector returns a constant (never invalidates) | **all nine** relevant tests fail |
| detector reverts to the broad token | every irrelevant test fails, plus `J1` and `J3` |
| one trigger removed | `B2` fails and the fail-safe engages, degrading to the broad token |

## 11. Pool context (§O)

Both caches moved to the new gate together, per §I — there is still **one**
detector and one shared recomputation.

| | |
|---|---|
| `O1` | an irrelevant write rebuilds nothing **and recomputes no digest** |
| `O2` | a relevant write **rebuilds** the context, moves the digest, and the context's college count rises by exactly one |
| `O3` | staleness and the context share a single recomputation, and the context's stamped token equals the current one |

A9.1's `K4` previously asserted `digestRecomputed: true` for a coach write —
accurate then, because the context was kept only *after* a ~890 ms confirmation.
It now asserts `false`. What the test guards is unchanged.

## 13. Migration (§H)

WAL-consistent 313 MB copy, three passes, then two more:

**19 business tables, zero row-count changes.** `roster_players` 286,002 →
286,002; `colleges` 2,700 → 2,700; `recruiting_arrivals` 88,847 → 88,847.
`integrity_check` ok, `foreign_key_check` 0.

The only differences are the new structures: `corpus_revision` (1 row) and the
9 triggers. Empty database: idempotent over two passes, 9 triggers, revision 0.

**One observation, not a defect introduced here.** The revision climbs by
exactly **28 on every migration pass** (84 → 112 → 140), traced to 28 `colleges`
UPDATEs that `migrate()` performs on every boot regardless of need. The row
count never changes, so these rewrite identical values. The practical effect is
one corpus-cache invalidation per process start, which costs nothing because
the cache is empty at that point. A9.7B made this visible; it did not create it,
and fixing a migration backfill is outside this phase.

for — that a write V2 cannot see never changes what V2 believes — is unchanged
and still asserted.

A9.7's `P3` was written as a characterisation test explicitly so it would be
inverted when this landed. It has been, and its original measurements are kept
verbatim: rewriting them would erase the evidence for the decision rather than
record it.
