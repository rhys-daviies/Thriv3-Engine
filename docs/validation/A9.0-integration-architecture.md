## §B–C Freeze adoption and guard

`docs/validation/V2-PROPOSED-FREEZE.md` → **`docs/validation/V2-FREEZE.md`**,
promoted by `git mv` so the proposal stays in history at `003d144`. It gains
the adoption block and the three permitted justification classes —
`DEMONSTRATED_DEFECT`, `MATERIAL_EVIDENCE_IMPROVEMENT`,
`REAL_WORLD_OUTCOME_EVIDENCE` — with the explicit statement that a surprising
individual ranking is not one of them.

The guard is `shared/matching/v2/freeze.js` (the contract as data) and
`shared/matching/v2/freeze.test.js` (11 checks): byte digests of all 11 scoring
files; weights; gates; the frozen scalars; `GRADE` still MEASURED|PARTIAL;
majorFit positive-only; Playing Pathway Policy B; the four supported
associations; the A8.3 artifact digest; and that the freeze record itself is
present, adopted and names its classes.

**Engine identity is kept apart from corpus identity.** The guard opens no
database — F11 asserts that on the import lines. The corpus is supposed to
grow, and a guard that read growth as a scoring mutation would fire on every
roster import and be switched off within a week. Corpus identity remains
`a8CorpusGuard.js`, split supported/unsupported for that reason.

**Mutation-tested.** A Pursuit weight 0.50→0.55 fails F1+F2; a gate floor
0.05→0.10 fails F1+F3; restoring the majorFit measured zero fails F1+F6.

*(A first attempt at the weight mutant silently did nothing — the source reads
`0.50`, my edit targeted `0.5` — and the guard "passed". The mutation is now
asserted before the run, which is the only reason the hole was visible.)*

## §D Current architecture

### Backend

Express (`server/index.js`), ~590 lines of route mounting. `/api` behind
`requireSameOrigin` → `authRouter` → `attachOperator` → `requireOperator`.
Generic entity CRUD at `/api/entities/:table` plus purpose-built routers:
`campaigns`, `athleteProgrammes`, `programmeCoaches`, `manualOutreach`,
`evidence`, `matchingSummary`, `reports`, `mailbox*`.

**There is no matching route.** `server/routes/matchingSummary.js` reads
evidence; it does not rank.

### Frontend

`src/pages/player/PlayerWorkspace.jsx` with tabs: Profile, **Matching**,
Evidence, Campaign, Decision, Engagement, Philosophy, Reports. Matching
surfaces live in `MatchingTab.jsx`, with `SpecificSearch` / `SpecificSchools` /
`SpecificSchoolDetail` for requested programmes, `CriteriaRanking` and
`PriorityTokens` for preferences, `SuppressedProgrammes`, and
`ActionableRecommendationsState`.

`MatchingTab` already separates the two ideas the V2 design needs:
*recommended* ("what the matching engine ranked, the Top 100") and *specific*
("what somebody ASKED FOR — a relationship, not a rank").

### §D Data flow — and the finding that drives everything

**V1 runs in the browser.** `PlayerWorkspace` imports `analyze` from
`src/lib/playerAnalysis.js`, which:

1. fetches **all colleges** for the sport (`entities.College.filter`);
2. fetches **all roster rows** for the sport and season — **29,000** men's,
   **33,251** women's;
3. fetches all `GraduatingSenior` records (997 / 1,113);
4. builds the roster index client-side;
5. calls `rankMatches` **synchronously in the browser**;
6. persists the Top 100 to `players.recommendations` (TEXT) and ranks 101–150
   to `reserve`.

Campaigns then read `players.recommendations` as a pointer, and
`identifyModel()` **infers** which matcher produced it from the breakdown
shape, saying so in terms: *"Inferred from the stored breakdown, not recorded
by the analysis run."*

**V2 cannot follow this path.** `buildPoolContext` needs `recruiting_arrivals`
— **88,823 rows** V1 never touches — plus a market index and state centroids.
V2 also retains the full ranked universe (824–1,100 programmes), not 100 + 50.
Shipping that to a browser is not an option.

### Measured cost

| | |
|---|---|
| `buildPoolContext` | **939 ms**, once per sport |
| `runPursuit` per athlete, warm | **24.4 ms** over 1,205 programmes |
| minimal full-universe payload | **64 KB** for 824 ranked |

The expensive part is the context, and it is shared by every athlete of that
sport.

## §G Ranking bands

Derived from the existing workflow, not invented: `MatchingTab` already works
in "the Top 100 we act on" plus "what somebody asked for", and campaigns
already consume the Top 100 as the outreach slice.

| band | ranks | what it means operationally |
|---|---|---|
| `PRIORITY_OUTREACH` | 1–25 | the first contact wave |
| `STRONG_PURSUIT` | 26–50 | the second wave |
| `VIABLE_CONSIDERATION` | 51–100 | completes the outreach slice |
| `BROADER_UNIVERSE` | 101+ | real, ranked, retained, searchable; not auto-outreach |
| `LIMITED_DATA` | — | not enough evidence to rank. **Not a band of the ordering** |

Boundaries are the ones A8's outlier selector already treats as operationally
meaningful (25/26, 50/51, 100/101, 250/251), so nothing new is asserted.

**One ranking model.** Bands are a view over the single full-universe Pursuit
ordering. A8 measured 600–975 adjacent pairs per athlete differing by < 0.001,
so the UI must not imply #100 and #101 are materially different — but it must
keep the exact rank, because the ordering is what the engine actually computed.

## §H Contribution gate

V2 refuses without a resolved contribution: Financial is required in Pursuit,
so an unresolved family yields **0 ranked, 1,422 LIMITED_DATA**. That is
correct and must never be softened into $0.

- **Backend.** `POST /api/players/:id/matchmaking` returns `409` with
  `{ error: "CONTRIBUTION_UNRESOLVED", state: "NEEDS_CONFIRMATION" }` rather
  than computing a universe of refusals.
- **API state.** `contributionState` is a first-class field on the result,
  always one of `STATED` | `NOT_A_CONSTRAINT` | `NEEDS_CONFIRMATION`.
- **Frontend.** The Matching tab shows a resolution prompt instead of an empty
  list: *"Matching needs to know what the family can contribute each year.
  Nothing is assumed."* With the three options, `NOT_A_CONSTRAINT` worded as
  "there is no fixed limit" — not "unlimited".
- **Where it belongs.** `ProfileTab` / `EditPlayer`, beside the existing
  budget fields, required before the Matching tab will run — not at account
  creation, which would block an operator mid-intake.
- **Operator recovery.** The prompt links straight to the field; resolving it
  and returning re-enables compute. No partial result is ever stored.

## §I Major preference UX

A declared major legitimately reshapes the list — 569 of 1,229 programmes carry
positive evidence — so it must be visible and removable.

- Lives with the other athlete preferences in `ProfileTab`, surfaced as an
  active chip in `MatchingTab` beside `PriorityTokens`: *"Ranking is boosting
  programmes known for exercise science."* with a one-click remove.
- Changing or removing it recomputes (24 ms; no job, no spinner worth showing).
- **The positive-only limitation must be truthful.** Where majorFit refuses,
  the card says *"We don't know whether this programme offers exercise
  science — our major records cover each institution's largest fields of
  study."*
- **Forbidden copy**, carried into the explanation vocabulary's
  `FORBIDDEN_LANGUAGE` list at implementation time: "does not offer",
  "not offered", "no such major", "lacks". A8.2's T10 already guards the
  refusal phrase; the UI needs the same guard.

## §J LIMITED_DATA and unsupported UX

Three distinct states, never collapsed into "bad match":

| state | user-facing meaning | action |
|---|---|---|
| SUPPORTED + RANKED | a ranked pursuit case | normal card |
| SUPPORTED + LIMITED_DATA | *"We can't rank this yet — no 2026 roster on file"* (named from `missingLayers`) | inspectable, searchable, flaggable; can enter outreach as a requested school |
| UNSUPPORTED_ASSOCIATION | *"Thriv3 has no eligibility rule for NJCAA, so it can't be ranked."* | inspectable; explicitly not a quality judgement |

The LIMITED_DATA reason is derived from the refusal codes already in the
contract — Opportunity (no roster / no readable positions), Recruitability (no
arrivals), Financial (no cost basis) — so the message names the missing
evidence rather than apologising vaguely. 93–144 supported programmes per
athlete are in this state; 481 programmes are unsupported.

## §K Full universe and Top 100, and §K Specific Search

One ordering. The Top 100 is a slice of it.

- Default view: Top 100, banded as §G.
- `#101+` reachable by paging the same list — already the shape
  `MatchingTab`'s `page` state uses.
- **Specific Search keeps no scoring of its own** and gains none.
  `SpecificSearch` already queries the `athleteProgrammes` API for a
  *relationship*, and `MatchingTab` already reads a rank off `recommendations`
  to display alongside it. The only change: read the rank from the **full
  universe** rather than from the stored Top 100, so a requested school at
  #431 shows "#431 of 824 ranked" instead of nothing.
- A requested school that is LIMITED_DATA shows its state and missing evidence
  in place of a rank, and stays actionable.
- A requested school in an unsupported association shows the eligibility-rule
  message and stays actionable.

## §L Outreach dependencies

Campaigns read `players.recommendations` and freeze a snapshot against that
pointer; `identifyModel()` infers the model from breakdown shape.

Required for V2, without changing outreach architecture now:

1. Top 100 continues to feed outreach — unchanged, it is the same slice.
2. Requested schools enter outreach through the existing `athleteProgrammes`
   relationship path, which is already rank-independent.
3. **LIMITED_DATA must not be read as a low score.** Any consumer that sorts or
   filters on a numeric score needs an explicit state check, because V2 emits
   `null`, not `0`.
4. Unsupported schools must not be silently dropped — they are absent from the
   ranking by design, and the campaign surface should say so if one is
   requested.
5. Explanation is available per programme for personalised drafting; the
   evidence vocabulary's forbidden-language guard already applies.

Coach Recruiting Intelligence stays separate.

## §M Compute and persistence — recommendation

**Hybrid: synchronous compute behind the API, with the result persisted and
versioned.**

Justified by measurement, not preference. The per-athlete cost is **24 ms**;
the 939 ms is the per-sport context, which caches in the server process and is
shared across every athlete of that sport. A queue would add operational
surface to hide 24 ms.

- Compute on demand at `POST /api/players/:id/matchmaking`, and on preference
  change (major, priorities, contribution).
- Cache `buildPoolContext` per sport in process, keyed by the **supported
  corpus digest** so a corpus refresh invalidates it rather than serving a
  stale index.
- Persist the full result — 64 KB minimal, a few hundred KB with explanations —
  for reproducibility, campaign pointers and audit.
- Persist the **full universe**, not the Top 100, so `#101+` and Specific
  Search read from one stored ordering.

Explicitly rejected: client-side compute (needs 88,823 arrivals in a browser);
async job (adds a queue to hide 24 ms); pure synchronous without persistence
(breaks campaign snapshots and reproducibility).

## §N Versioning

The repo already admits the gap: `identifyModel()` says the model was
*"Inferred from the stored breakdown, not recorded by the analysis run."*

Every persisted result records explicitly:

```
matcherVersion   "v1" | "v2"
engineFreeze     FREEZE_ENGINE_HEAD for v2; null for historical v1
corpusDigest     the SUPPORTED digest at compute time
computedAt       timestamp
```

This separates the four things that must not be confused: a historical V1
result, the accepted V2 engine, the same engine over refreshed evidence, and a
future V3. `identifyModel()` stays, demoted to a fallback for rows written
before versioning existed — it is the only thing that can classify them.

## §O Rollout

| stage | gate to the next |
|---|---|
| **1. Operator-only** — V2 behind an operator flag, V1 still default; both visible for the same athlete | operators can explain every Top-25 difference |
| **2. Selected real athletes** — V2 default for a named cohort; V1 computed in parallel and stored | no evidence-truthfulness complaint; outreach proceeds normally |
| **3. Compare** — consultant feedback plus the §P outcome data | enough replies to see whether rank relates to response |
| **4. Default V2** — new analyses are V2; historical V1 results stay readable | one full campaign cycle without a scoring escalation |
| **5. Retire V1** — only after a dependency audit confirms no live consumer, and a rollback window has passed | — |

**Rollback:** the flag flips back; V1's path is untouched throughout and
`players.recommendations` keeps its V1 shape until stage 4. Because every
result is versioned, a mixed estate is readable rather than ambiguous.

V1 is **never deleted** — it remains the frozen comparison instrument and the
backtest engine.

**Synthetic validation is not a substitute for outcomes.** Everything through
A8.3 was synthetic. Stage 3 is the first real evidence, and it is the only
route to `REAL_WORLD_OUTCOME_EVIDENCE` in the freeze record.

## §P Live data collection

Recorded at outreach time, so the state is the one that was acted on:

`programmeId` · `rank` · `band` · `pursuit` · each layer's value, state,
coverage and grade · `missingLayers` · `matcherVersion` · `engineFreeze` ·
`corpusDigest` · `computedAt` · `sentAt` · `openedAt` (where reliable) ·
`repliedAt` · `replyClassification` · `interested` · `callScheduled` ·
`offer` · `committed` · coach and programme identity.

**ATHLETE→PROGRAMME FIT stays separate from PROGRAMME→ATHLETE INTEREST.** The
first is what V2 scores; the second is what a reply measures. Collapsing them
is how a response-rate model gets mistaken for a fit model. Nothing is trained
or tuned on this; it accumulates until stage 3.
