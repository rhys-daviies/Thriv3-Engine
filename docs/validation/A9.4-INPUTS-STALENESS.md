## 1. The bottleneck, confirmed against current code

A9.3 reported ~880 ms and named the cause. §B required re-deriving it rather
than trusting that, so the whole endpoint was taken apart against the live
corpus:

| component | time |
|---|---|
| `currentRun` (find the row) | 0.050 ms |
| `readRun` (1,205 rows → 570 KB payload) | **5.705 ms** |
| `runStaleness` | **1,480 ms cold · ~890 ms warm** |
| ↳ input snapshot + two digests | 0.110 ms |
| ↳ **`corpusDigests`** | **1,281 ms** |
| ↳ engine identity (string compare) | ~0 ms |
| `corpusChangeToken` | **0.007 ms** |

Three consecutive `runStaleness` calls cost 1,417 / 908 / 889 ms — nothing was
cached. The diagnosis holds exactly: **serving the answer was 5.7 ms, and
deciding whether it was still fresh was 890 ms, every single request.**

`corpusDigests` reads every college, roster row and arrival for both sports,
once per universe, and hashes them. Twelve table scans.

## 2. The cache — A9.1's architecture, lifted rather than copied

`cachedCorpusDigests` now lives in `server/lib/v2/corpusIdentity.js`, beside
the identity it guards, and **both** callers use it:

```
runStaleness      (A9.2)  — was recomputing on every current-run request
poolContextFor    (A9.1)  — was computing it inside its own context cache
```

§C asked for one shared implementation, and this is the operational benefit:
when the token moves because 7B wrote a coach row, the service and the
staleness check now pay for **one** recomputation between them rather than two.

The digest definition, the two-universe split, the season and the fact that
corpus identity is **global over both sports** are all untouched. A
men's-soccer run still goes stale when women's roster data moves — asserted in
`C1`, because narrowing that would be a semantics change wearing a performance
change's clothes.

### Keyed on the connection, not just the season

`corpusChangeToken` is `data_version` + `total_changes()`. The second **resets
when a connection opens**, which has a consequence worth stating plainly:

> Two freshly-migrated databases both report the token **`1:0`** — measured,
> not assumed.

So a process holding two corpora can produce identical tokens over completely
different data. A cache keyed on the season alone hands the second database the
first one's identity and calls it a hit. The cache is therefore a `WeakMap`
keyed on the `Database` object, which makes that class of bug unreachable
rather than something a reset call has to remember to prevent.

### The direction it is wrong in

The token is a **change detector, never an identity**. It is deliberately
over-sensitive: a coach write moves it although nothing V2 reads changed. That
costs one recomputation and never a stale answer. The reverse — a relevant
write the token misses — needs schema-level DDL, which does not increment
`total_changes()`; that defeats `poolContextFor`'s cache identically and is
bounded by process lifetime. Documented, not hidden.

## 3. Invalidation, proven

`server/lib/v2/corpusDigestCache.test.js` — 13 tests. Every "must invalidate"
case is paired with a "must not change the answer" case, because **a cache that
never caches passes every invalidation test ever written**.

| | case | result |
|---|---|---|
| D1 | no writes | 1 computation, then 10 hits |
| D2 | unrelated write (`coaches`, 7B-shaped) | token moves → re-verified → **`CORPUS_CHANGED` false** |
| D3 | supported roster write | invalidates → **stale** |
| D4 | supported college write | invalidates → **stale** |
| D5 | `recruiting_arrivals` write | invalidates → **stale** |
| D6 | opposite-sport relevant write | invalidates → **stale** (identity is global) |
| D7 | 25 repeated staleness checks | **1** computation, 24 hits |
| D8 | cache reset | recomputes, same answer |
| D9 | two connections, identical token | neither served the other's digest |
| D10 | a cache that ignored the token | reproduced, and caught |
| D11 | the token moves for every write type used above | — |

Mutation-tested:

| mutation | caught by |
|---|---|
| ignore the token entirely | D2, D3, D4, D5, D6 |
| key on season only, not the connection | D7, D8, **D9** |

**D9 originally proved nothing.** It compared the shared test database against a
fresh one — whose tokens could never match, so it passed with or without the
connection key. Rewritten to construct the actual collision (two migrated
in-memory databases, one write each, identical `1:1` tokens, different
corpora), it now fails under the season-only mutation.

## 4. Performance, before and after

Against the live corpus, full endpoint (`readRun` + `runStaleness`):

| | A9.3 | A9.4 |
|---|---|---|
| cold (first after process start) | ~1,800 ms | 1,800 ms |
| **warm, repeated** | **~890 ms** | **6–17 ms** |
| `runStaleness` alone, warm | ~890 ms | **0.02–0.08 ms** |
| after unrelated write | ~890 ms | 1,437 ms once, then 13 ms |
| after relevant write | ~890 ms | 1,524 ms once, then 6 ms |
| run-by-id (no staleness) | 15.9 ms | 9.5 ms |

In a real browser, against the 549 KB payload:

| | |
|---|---|
| `runs/current` warm median | **11.2 ms** |
| `runs/:id` (no staleness) | 9.5 ms |

§E's target was "the same broad operational range as persisted-run retrieval,
not ~900 ms". 11.2 ms against 9.5 ms — **the freshness check is now effectively
free**, and the endpoint is ~79× faster warm.

The cold path is unchanged by design: the first request after a restart must
take the identity, and no cache can avoid that.

## 6. Family contribution — §G

Reused unchanged. All three frozen states are representable and distinct:

- **STATED** — an amount, validated to whole dollars
- **NOT_A_CONSTRAINT** — "Cost isn't a meaningful factor", stored with a null
  maximum, resolving to `Infinity` for V1 and ranking for V2
- **NEEDS_CONFIRMATION** — blocks V2, carries the legacy band as *context*,
  explicitly "not read as a maximum"

`$0` is never rendered or written for an unresolved contribution — asserted in
`T3` and `N3`. Zero is the full-scholarship request and means the opposite.

What A9.4 added is **visibility**: the contribution now appears on the
Matchmaking preference summary, first, using `contributionSummary`'s own words.

## 7. Blocker recovery — §H

A9.3 routed the 409 to Edit Profile and stopped. The loop is now closed:

```
409 → "Add the family contribution" → /edit?return=matching
    → answer → Save → back on Matchmaking, run unchanged, nothing generated
    → operator clicks Generate / Refresh
```

`?return=` is an **allow-list of one**. A URL is something anyone can hand an
operator, and resolving free text into `navigate()` would be an open redirect
in a product holding athlete records. `H3` asserts `https://evil.test`,
`../../admin` and an unknown tab all fall back to the player page.

Verified end to end in a browser against Ryan Billings — a real athlete whose
`budget_range` is `Undeclared` and who genuinely returns 409 — answering
`NOT_A_CONSTRAINT` and returning to a screen that still said *"No matches
generated yet"*.

## 8. Intended major — §I, §J

`IntendedMajorField` replaces the bare input, for one reason:

> An operator typing an unplaceable major saw it save, saw it on the profile,
> and saw it listed as a ranking preference — while `majorFit` returned
> NOT_APPLICABLE, which costs **no coverage**, so nothing anywhere looked wrong.

The field now answers while it is being typed, through `academicIntentState` —
the same function the scorer calls, not a second taxonomy:

| state | what the field says |
|---|---|
| VALID | "Thriv3 reads this as **Kinesiology**, and will use it when ranking." |
| UNDECIDED | "reads as undecided… correct outcome until the athlete has a field in mind" |
| UNSUPPORTED | "cannot currently map this… **will not affect ranking**. Try the subject itself" |
| MISSING | "Optional. Left blank, Thriv3 ranks on everything else" |

Removal is a real `<button type="button">Remove</button>`, keyboard operable
and named, shown only when there is something to remove. The verdict carries
`role="status"` so it is announced, and is `aria-describedby` the input.

**Every sentence is about what Thriv3 can map. Not one is about what an
institution offers.** `J1` renders six different major values and checks all
eight forbidden spellings plus "no programmes offer" / "not available at" /
"no school offers". `J2` asserts the word *institution* never appears.

> A test drafted here asserted "Sports Management" was UNSUPPORTED and failed:
> the taxonomy places it as Kinesiology. The tests now use *Equine Studies* and
> *Viticulture* — real degrees the fourteen families genuinely cannot place.

## 10. Save → stale → refresh — §L, §M

Staleness is **never set by hand**. It falls out of
`inputDigest(inputSnapshot(player))` disagreeing with the snapshot stored beside
the run.

Proven for every matchmaking input — contribution amount, contribution state,
major add / change / **remove**, and each of the three priorities — and, just as
hard, for the other direction:

> **L9.** `guardian_name`, `guardian_email`, `club_name`, `evaluation` and
> `time_zone` do **not** mark a run stale. Without this, every test above would
> pass while the feature was useless: an operator correcting a phone number
> would be told their rankings are out of date.

**§M — no automatic recompute.** Every one of the eight staleness tests also
asserts `runsCreated === 0`. `M1` walks six consecutive edits and holds the run
count at exactly 1, then creates the second run only on an explicit ask. `H4`
asserts the save request list contains no `/matchmaking` call at all. And the
browser confirmed it: after saving, the screen still read *"No matches
generated yet"*.

`L10` asserts the run row is **byte-identical** after an edit — history is not
rewritten to match the present.

Mutation-tested:

| mutation | caught by |
|---|---|
| `guardian_name` added to `INPUT_FIELDS` | **L9 only** |
| staleness stops comparing inputs | the 8 marks-stale tests |

## 11. Current profile vs the profile this run used — §O

`runView` now carries **six named preference fields** off the persisted
snapshot — not the snapshot. `inputSnapshot` holds twenty inputs including
`gpa`, `sat_score`, `state` and `nationality`; none is needed to answer "is
this still what the ranking was built from", and carrying them to a screen that
does not show them is how a payload becomes a place person-level data
accumulates.

The A9.3 privacy test was **narrowed, not relaxed**: `V16` now names the
excluded fields and asserts their values do not appear in the serialised run —
a check that bites on a field being added, where `toBeUndefined()` on the
container would not.

Comparison is **raw**, matching `inputDigest`. "exercise science" →
"Exercise Science" makes the run stale, so the screen must agree it changed.

Verified live: changing two inputs marked exactly those two — *"Major
preference: business · changed"*, *"Academic strength: Extremely important
(5 of 5) · changed"* — while contribution and the two unanswered priorities
stayed unmarked.

## 12. Accessibility — §Q

Labels on every control (`htmlFor`/`id` via `useId`). The 1–5 importance scale
is radio buttons with text labels, never colour. `NOT_A_CONSTRAINT` and
`NEEDS_CONFIRMATION` are full sentences. Remove is a named button. The major
verdict is `role="status"`. The changed marker is the **word "changed"**, not a
dot or a hue. Stale state is announced in the run bar's own text.

## 13. V1 coexistence — §R

Worth stating precisely, because the obvious assumption is wrong:

> **V1 does not ignore the V2 contribution fields.** `shared/matching/pool.js`
> passes `contribution_state` and `max_annual_contribution_usd` into
> `familyBudgetCeiling`.

The difference is what each does with *unanswered*. V2 refuses. V1 returns
`undefined`, which its affordability criterion scores at its neutral prior and
labels as assumed — so an athlete whose family has not answered still gets a V1
list, exactly as before. `R1`–`R3` pin this, including that the legacy band
still answers for V1 and that `NOT_A_CONSTRAINT` is `Infinity` to V1 and
rankable to V2.

`MatchingTab.jsx` remains byte-identical. `?matching=v1` verified in the
browser.
